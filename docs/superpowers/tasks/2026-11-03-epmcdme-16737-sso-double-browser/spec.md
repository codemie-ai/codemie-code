# EPMCDME-16737 - One SSO expiry opens exactly one browser

## Problem

After an SSO session is revoked server-side, request A gets the oauth2-proxy redirect and a detached sign-in starts. If the sign-in finishes inside the 5 s credential throttle window, request B (the resumed prompt) is still sent with the old cookies. It gets a redirect too, so the plugin re-marks auth invalid and answers 401 "did not complete". The next prompt, once the 30 s cooldown has passed, finds the marker and opens browser #2. Evidence: `technical-analysis.md` section 8, reproduced end to end; control with request B at 6 s opens one browser.

Root causes, all in the SSO provider plugin:
- `CredentialRefresher.refresh()` ignores a sign-in that finished inside its window (`credential-refresh.ts:76-85`; it only reacts to the marker invalid-then-cleared edge, which a fast sign-in never lets it observe).
- The expiry plugin acts on any redirect without asking whether the request carried cookies that a later sign-in already replaced (`sso-session-expiry.plugin.ts:76-118`).
- The metrics writer does the same on an auth failure: `MetricsApiClient.sendMetric` marks auth invalid for a send made with cookies read before the sign-in (`metrics-api-client.ts:90-95`). Every uploader reads cookies once and sends later: the daemon's sync tick (`sso.session-sync.plugin.ts:262`), the hook's start, end and sync, the desktop runtime, and the codex, pi and opencode incremental syncs. A response, a later send of the same pass, or a 5xx/network retry (1/2/5 s) can land after the sign-in cleared the marker and write one with a newer `detectedAt`. The OTLP forwarder is not a writer: it keeps an in-memory stale flag only (`otlp-spool/auth-state.ts`).
- The hook gate trusts any marker, whatever its age relative to the last successful sign-in (`sso.auth-gate.ts:102-116`).
- The post-success `cooldown` outcome shares text with the post-failure one: "did not complete. Run `codemie profile login`" (`sso.detached-login.ts:345`), and `profile login` bypasses the lock, so it opens another window.

## Goals and behavior

0. **One lock reader.** `sso.detached-login.ts` exports `getLastSignInAt(source)`: the lock's `succeededAt`, or null. `source` is a `PlatformUrlSource`-shaped object (type-only import from `codemie-auth-helpers`). It never throws (any read error returns null) and ignores `source` today (the lock is global). The refresher passes `this.params` (already that shape); the gate passes its `source` (`sso.auth-gate.ts:82`). A later per-profile keying calls `getPlatformUrl(source)` inside `sso.detached-login.ts` only, so no caller changes.
1. **Refresher notices a finished sign-in.** The shared store reader (item 2) remembers the last `getLastSignInAt` value it acted on; `refresh()` bypasses the throttle when the current value is non-null and `!==` that one (not "greater than `lastRefreshedAt`": a stepped-back clock must not turn every call into a store read). The value is captured and remembered together with `lastRefreshedAt`, before the store read's await, on every attempt, success or failure (a failing store costs one read per window, not one per call; `refreshNow()` records it too, so the next `refresh()` does not re-read). The existing marker-edge bypass stays. Turns the red `credential-refresh.test.ts` green.
   - **Followers of a bypass read.** `refresh()` keeps the promise of a read it started because of a bypass (changed stamp or marker edge). A `refresh()` call that arrives while it is pending awaits it and returns its result: the new credentials, or the unchanged snapshot when the read failed, timed out or came back empty. A read started only because the throttle lapsed is not joined: followers keep today's immediate return of the snapshot. The decision (consume the edge flag, compare the stamp, set `lastRefreshedAt`, remember the stamp, publish the pending promise) runs with no await between its steps, after the call's own marker and stamp reads, so two calls can never both start a bypass read or let one slip past the other. The pending slot is cleared in a `finally`. `refreshNow()` ignores this promise (its own-reads-only rule below stays).
2. **Superseded cookies are not an expiry.** On a redirect to `/oauth2/start`, before marking auth invalid or starting a sign-in, the expiry interceptor asks the shared check below (refresher reached through `PluginContext.credentialRefresher`, now passed to the interceptor).
   - `refreshNow()` is a new `CredentialRefresher` method sharing one private store reader with `refresh()`. On success it assigns `current` and `lastRefreshedAt` as `refresh()` does (so the re-sent request already has the new cookies) and returns the stored credentials; on a failed or empty read it leaves `current` unchanged and returns null.
   - Reads are numbered when they start; a read assigns `current` only if no later-started read has assigned already (an older read finishing late never overwrites a newer snapshot). `refreshNow()` joins only an in-flight read that a `refreshNow()` call started, otherwise starts its own; it never joins the throttle read of `refresh()`, which may predate the sign-in.
   - The private reader runs the store read under a deadline (`STORE_READ_DEADLINE_MS`, exported from `session/cookie-auth.ts`, initial value 3 s, set from the measurement in Constraints). A timeout is a failed read: `refresh()` keeps its snapshot, `refreshNow()` returns null, the in-flight slot is cleared in a `finally`, and a late result of the timed-out read is ignored.
   - One exported pure `buildCookieHeader(cookies)` replaces the header-building rule of `SSOAuthInterceptor.onRequest` (entries with an empty name or control characters dropped; pairs joined with `; `, `sso-auth.plugin.ts:64-87`). `onRequest` keeps its warning log and its throw when nothing is left. `sso.session-sync.plugin.ts` drops its private, non-filtering `buildCookieHeader` (`:33-37`) and uses the shared one, so every sender of the compared header follows one rule.
   - **One shared check**, `sentCredentialsSuperseded(sentCookieHeader, source)`, in the same new neutral module as `buildCookieHeader`: `src/providers/plugins/sso/session/cookie-auth.ts` (the session layer: proxy plugins already import from it, and the hook, desktop and agent uploaders can use it without reaching into the proxy layer; the expiry plugin must not import a sibling plugin). `source` is any object with `refreshNow(): Promise<{ cookies: Record<string, string> } | null>`, which `CredentialRefresher<SSOCredentials>` satisfies structurally. The check calls `source.refreshNow()` and returns true only when that returns credentials, the sent header and `buildCookieHeader(fresh.cookies)` are both non-empty, and the two whole strings differ. It returns false in every other case (no source, no header, null, a throw, empty builder result) and never throws; a header is never parsed back and neither side is logged. "Unsure" means "behave as before": a genuine revoke is never swallowed. The expiry plugin and the metrics writer (item 5) both go through it; neither has its own comparison.
   - True: the request was built from superseded credentials. Drain the 302 body first, in its own try (a drain failure is ignored and logged at debug): the synthetic response built with `tools.fromBuffer` does not consume the upstream one, and the upstream sockets are keep-alive. Do NOT mark invalid, do NOT start a sign-in. Log one debug line ("request carried superseded credentials", no cookie content). Return a synthetic 401 saying the session was just renewed and the prompt should be re-sent, built by a new module-level `syntheticUnauthorized(response, tools, message)` that only this branch calls. No request replay.
   - False: unchanged behavior (mark invalid, start sign-in, 401 from `describeLogin`). The 401 is always emitted; the raw 302 never leaks.
3. **Gate clears a provably stale marker.** In `ensureCodeMieSsoAuth`, when no API key is set, a marker that applies to this profile (`markerAppliesToProfile`) and has `detectedAt` strictly less than `getLastSignInAt(source)` is stale: the gate removes it with the existing `clearAnalyticsAuthStatus()` and proceeds as if no marker existed (valid stored credentials -> `ok: true`). With an API key the check is skipped (a sign-in proves nothing about an API key), so the no-retry rule at `:115` and today's blocking are untouched.
   - Both values are epoch-millisecond `Date.now()` values written on the same host; the check needs a non-null stamp and a finite `detectedAt`; equal is not stale.
   - Right before the clear the gate re-reads marker and stamp and clears only if the condition still holds. A re-read marker that no longer meets it (re-written after the sign-in) is the one the gate acts on: it blocks and signs in, nothing is cleared. A gone marker is no marker. A marker for another profile is never cleared.
   - `clearAnalyticsAuthStatus` is best-effort and reports no failure. The decision rests on the staleness judgment, not on the unlink: the gate proceeds, the file stays, the next pass retries. Nothing is escalated beyond the helper's debug line.
4. **Split the post-success cooldown.** `acquireLock` returns a new outcome `signed-in-recently` for the `succeededAt`-within-30 s branch; `cooldown` stays for the post-failure/dead-process branch (`sso.detached-login.ts:183`). `describeLogin` gets an explicit case, and its `default` branch a `never` check so a forgotten member fails the build. Text, accurate after a finished sign-in and after a repeat rejection: "A sign-in finished moments ago; re-send your prompt. If it is rejected again, wait about N seconds and re-send: a new sign-in then opens automatically.", with N = `Math.round(COOLDOWN_MS / 1000)`. It never contains "did not complete" or `codemie profile login`. The `cooldown` text and all `wait.status` texts are unchanged.
5. **Metrics writer honors superseded credentials, at every sender.** In `MetricsApiClient.sendMetric`, on an auth failure (`isAuthFailure`) of a request sent with cookies (not API-key mode), the client first asks an optional injected `credentialsSuperseded(sentCookies)`; when it returns true the client does not call `markAnalyticsAuthInvalid` (it logs a debug line, no cookie content). Everything else is unchanged: the error is classified, retried or thrown as before, the delta stays failed and is re-sent next pass with refreshed cookies, and a real rejection (false, absent callback, callback error) marks as before.
   - Plumbing, no new import from the session layer into the proxy layer: an optional `credentialsSuperseded?: (sentCookies: string) => Promise<boolean>` on both `ProcessingContext` declarations (`sso/session/BaseProcessor.ts:15` and `agents/core/session/BaseProcessor.ts:15`, kept identical), `MetricsSenderOptions` and `MetricsApiConfig` (`metrics-types.ts:150`). `MetricsApiClient` types its config as `Required<MetricsApiConfig>`, so its constructor literal supplies the default (`async () => false`); `MetricsSender` forwards the option in the `MetricsApiConfig` it builds field by field (`metrics-api-client.ts:327-337`).
   - **Where it is wired.** `metrics-sync-processor.ts:187` passes `context.credentialsSuperseded`; it is the only `MetricsSender` built for every `SessionSyncer` run (daemon, hook sync, codex, pi, opencode, desktop sync), so those need no sender edit, only a context that carries the callback. Four `new MetricsSender` sites are built directly (`hook.ts:1094,1347`, `DesktopTelemetryRuntime.ts:393,433`) and pass the callback themselves.
   - **How a site gets the callback.** The check must re-read the exact store the sent cookies came from, so the callback is built where the cookies are read, from the same reader. Two helpers in `session/cookie-auth.ts`: `readCookieAuth(read)` calls `read()` once, returns `{ cookies: buildCookieHeader(...), credentialsSuperseded }` (cookies `''` when nothing usable), and its `credentialsSuperseded(sent)` calls `sentCredentialsSuperseded(sent, { refreshNow })` where `refreshNow` re-runs the same `read()` under `STORE_READ_DEADLINE_MS` (a throw or timeout is null, hence false). `readAnalyticsCookieAuth(ssoUrl, env, overrides?)` is `readCookieAuth` over `getStoredAnalyticsCredentials(ssoUrl, env, overrides)` (loaded lazily, as the callers do today) with the same arguments for the first read and the re-read. A process without a `CredentialRefresher` (hook, desktop, agent) keeps no snapshot, so the re-read is a plain unthrottled store read, made only on an auth failure. Sites replace their inline `Object.entries(...).map(...).join('; ')` with the helper, so every sent header comes from `buildCookieHeader`.
   - **Sites** (all unset in local-dev or API-key mode, where no cookies are sent):
     - daemon sync, `sso.session-sync.plugin.ts:178-185` (constructor; cookies refreshed per tick at `:262`): `(sent) => sentCredentialsSuperseded(sent, this.credentials)`, the refresher that built `context.cookies`.
     - hook sync context, `hook.ts:486-507`: `readAnalyticsCookieAuth(ssoUrl, config?.env, { provider: getConfigValue('CODEMIE_PROVIDER', config) })`; the context gets `cookies` and the callback.
     - hook SessionStart `hook.ts:1057-1101` and SessionEnd `:1316-1354`: the same call (same arguments), the callback passed to `new MetricsSender`.
     - desktop, `DesktopTelemetryRuntime.ts:351-382` (`buildProcessingContext`): `readCookieAuth(() => new CodeMieSSO().getStoredCredentials(credentialsUrl))`; the context carries the callback for `syncer.sync` (`:340`), and `:393,:433` pass `context.credentialsSuperseded`.
     - codex `codex.incremental-sync.ts:160-189`, pi `pi.incremental-sync.ts:335-364`, opencode `opencode.incremental-sync.ts:173-203` (`buildUploadContext`): `readAnalyticsCookieAuth(ssoUrl, env)`, the arguments they use today.
     - Not wired, by reason: cookies preset by the caller (`HookProcessingConfig.cookies`, `hook.ts:63,486,1058,1317`) have no store to compare, and a different login source would look superseded and hide a real revoke; the callback stays unset there and the writer marks as before. The `cookies: ''` contexts (`codex.plugin.ts:237,385`, `pi.plugin.ts:407`, `opencode.plugin.ts:242`, `opencode-metrics.ts:213`) only parse and never upload.

## Acceptance criteria

- AC1: With stored credentials replaced and the lock stamped with a `succeededAt` different from the one last acted on, the next `refresh()` returns the new credentials inside the 5 s window; an unchanged stamp does not bypass the throttle. A failed or empty read after a sign-in causes no second read inside the window. A `refreshNow()` while a throttle read of `refresh()` is still in flight starts its own read and gets the post-sign-in store; an older read finishing late does not overwrite the newer snapshot. Two `refresh()` calls made concurrently right after a stamp change both resolve to the new credentials from one store read; a call arriving during a plain throttle read returns the snapshot at once; a failed bypass read resolves its followers with the unchanged snapshot and leaves the slot free. This proves item 1 alone (no expiry plugin involved).
- AC2: A redirect on a request whose `cookie` header differs from `buildCookieHeader(fresh store)` yields a 401 and causes no marker write and no sign-in start; the 302 body was drained (`readBody` asserted, also when it rejects); afterwards `refresh()` returns the new cookies without time passing. Proves item 2 alone (the refresher is stubbed, item 1 not involved).
- AC3: A redirect on a request whose header equals the freshly built one (real revoke, including after a sign-in outside the post-success cooldown, and including a store holding an entry the builder drops) marks invalid and starts exactly one sign-in.
- AC4: If `refreshNow()` returns null or throws, the expiry plugin still returns a 401 and follows the AC3 path. A store read that never answers ends after `STORE_READ_DEADLINE_MS` as a null read, and the next `refreshNow()` starts a fresh read (the slot was cleared).
- AC5: Valid stored credentials plus a marker older than `succeededAt`: the gate returns `ok: true` and the marker file is gone. A marker newer than or equal to `succeededAt`, or one that a re-read before the clear shows to be newer, is not cleared and the gate blocks and signs in. A marker for another profile is not cleared. With an API key the marker is not cleared. A clear that does nothing still yields `ok: true`. With real marker files: stale marker cleared, a later genuine re-mark (fresh `detectedAt`) blocks.
- AC6: `describeLogin('signed-in-recently')` contains "re-send your prompt" and "wait" and neither "did not complete" nor "codemie profile login"; its seconds come from `COOLDOWN_MS`; `describeLogin('cooldown')` is unchanged.
- AC7: Fail, timeout and interrupt recovery, the API-key no-retry guards (`sso.auth-gate.ts:115`, expiry JWT guard `:64`) and `describeLogin(undefined)` are unchanged; existing tests pass except those that assert the post-success outcome name.
- AC8: Manual, with the ticket's `s4.sh` harness against a rebuilt build and restarted proxy daemon. Item 1 and item 2 are told apart by outcome and by the daemon debug line:
  - 8a, 0.15 s run: `browsers_total=1`, request B is answered by the upstream (200, valid token in the upstream log), and the "superseded credentials" line does not appear. A "just renewed" 401 here means item 1 did not fire: fail.
  - 8b, a request carrying the pre-sign-in cookie sent after the sign-in (held in flight, or sent with the captured old header): the "just renewed" 401, the superseded line appears once, `browsers_total=1`, no marker afterwards.
  - 8c, a real revoke after the sign-in and outside the cooldown: exactly one new browser.
  - 8d, metrics path: a sync send made with old cookies whose auth-failure response the mock delays until after the sign-in finished: no marker with `detectedAt` > `succeededAt`, the next prompt is not blocked, no second browser after 30 s.
- AC9: Metrics writer, with real marker files in a temp `CODEMIE_HOME` and a mocked `fetch`. Auth failure (401, and 200 + HTML) with `credentialsSuperseded` returning true: no marker. Returning false, throwing, or absent: marker written as before. A non-auth failure writes no marker either way. A send in the same pass made after the marker was cleared by a sign-in does not re-create it. In API-key mode the callback is not asked. The daemon's sync interceptor sets the callback from the refresher and not in local-dev mode.
- AC10: `sentCredentialsSuperseded` unit cases: differing headers true; equal, no source, empty sent header, null, throw, empty builder result false. `readCookieAuth` cases: the header equals `buildCookieHeader` of the first read; the callback re-runs the same reader (same arguments, asserted for `readAnalyticsCookieAuth`); a differing re-read true; equal, null, a throwing and a never-answering reader (after `STORE_READ_DEADLINE_MS`) false. The expiry plugin, the sync interceptor and `readCookieAuth` are the only callers of `sentCredentialsSuperseded`; none compares headers itself.
- AC11: Wiring, one case per site: `metrics-sync-processor` passes `context.credentialsSuperseded` to `MetricsSender` (absent stays absent); the hook sync context, SessionStart and SessionEnd senders, the desktop context and both desktop senders, and the codex, pi and opencode upload contexts each carry a callback whose cookies come from the helper and whose re-read uses the site's own reader arguments. With `HookProcessingConfig.cookies` preset or an API key, no callback. A grep finds no remaining inline `Object.entries(...cookies...).join('; ')` at these sites, and every non-test `new MetricsSender(` either passes `credentialsSuperseded` or is one of the unwired cases above.

## Non-goals

- No clearing of the marker on proxied success (ticket item 3, weakened by the user). The only clearing added is the gate removing a marker it has just proven older than the latest sign-in.
- No change to `markAnalyticsAuthInvalid`'s keep-the-first-`detectedAt` rule or to the marker util (it must not depend on a provider module).
- No change to `COOLDOWN_MS`, `LOCK_MAX_AGE_MS`, `CREDENTIAL_REFRESH_INTERVAL_MS`, or to the marker-edge bypass (it is the only signal for `codemie profile login`, which clears the marker but never stamps the lock; making it stamp is a separate behavior decision, no follow-up planned here).
- No change to the OTLP forwarder (`otlp-spool/auth-state.ts`, `forwarder.ts`): it never writes the marker, and its in-memory stale flag and resume path stay as they are.
- No default `credentialsSuperseded` inside `MetricsApiClient` or `MetricsSender`, and no supersession check for cookies a caller passed in instead of reading from the store.
- No retry of a superseded metrics send with fresh cookies in the same pass; the next pass does it.
- No change to `codemie profile login` or the Anthropic-shaped 401 body (known gap, separate); no client-specific 401 shape or retry header.
- No docs rewrite; no commit or push.

## Changes after approval

Follow-ups approved after the spec above was signed off. Where they conflict with the sections above, these hold.

- Replay through `tools.retry`: a redirect on a superseded request is replayed once with the fresh cookies, including requests without a body (GET, HEAD, DELETE), for which `retry` takes a null body. A replay that throws falls back to the "just renewed" 401; a replay that is itself the redirect runs the expiry path.
- URL-scoped sign-in stamp: `sso-login.lock` records the `url` of its own sign-in. A newer attempt carries the earlier success over as `lastSucceededAt` and `lastSucceededUrl`, and `getLastSignInAt(source)` returns a stamp only for the URL `source` resolves to (a lock without a URL matches every source). An attempt that could not be started is kept as a `discardAttempt` tombstone (a failed lock with no process and an old `startedAt`) so the earlier stamp is not lost with the file. The marker stays global.
- URL-scoped post-success cooldown: `acquireLock` blocks with `signed-in-recently` only when the success was for the same URL (compared normalised) or the lock records no URL (older versions). A request for another URL within the cooldown starts its own sign-in. The in-progress and post-failure decisions are unchanged and ignore the URL.
- Shared "mark unless superseded" helper (`markAuthInvalidUnlessSuperseded`, `session/analytics-auth-marker.ts`): used by the metrics client and the conversation client.
- Marker writers are three: the expiry plugin, the metrics client and the conversation client.
- With the `signed-in-recently` outcome the expiry 401 carries the sign-in text alone, without the "CodeMie SSO session expired." lead.

## Decisions

- Keep `cooldown` for post-failure and add a new outcome for post-success over renaming `cooldown`: keeps recovery paths and four test files untouched.
- Name the new outcome `signed-in-recently` over `cooldown-success`/`recovered`: reads as a state, not a timer. Builder may rename.
- One new exported read-only helper `getLastSignInAt(source)` over exporting `readLock`: smallest surface; taking the source object (not a URL built in the caller) keeps a later per-profile lock a one-file edit and keeps `credential-refresh.ts` free of `getPlatformUrl`.
- Refresher bypasses on a changed `succeededAt` (`!==`) over "newer than `lastRefreshedAt`": two processes' wall clocks must not decide it.
- Remember the stamp with `lastRefreshedAt` before the read, on every attempt, over remembering it only after a successful read: a failing store must not turn every call into a read.
- Followers of a bypass read await it over being served the old snapshot: after a sign-in a resumed agent often sends several requests at once, and each old-cookie follower would otherwise end in a "just renewed" 401. Followers of a plain throttle read keep the immediate snapshot: nothing changed for them.
- `refreshNow()` joins only reads that `refreshNow()` started, and reads assign by start order, over sharing one read with `refresh()`: a throttle read begun before the sign-in must not give a redirect the old snapshot.
- Store reads of the shared reader run under a deadline over unbounded: a hung keychain must neither hold the in-flight slot forever nor hold every redirect response; a timeout is a failed read.
- Compare whole `cookie` header strings built by one shared `buildCookieHeader` over comparing the sent header with the raw stored map, `expiresAt` or parsed pairs: a dropped store entry must not make every real revoke look superseded, `expiresAt` does not change on a server-side revoke, and the sent header is the only ground truth.
- Session sync adopts the shared builder over keeping its private non-filtering one (and over renaming it): the metrics comparison is sound only if both sides follow one rule.
- The hook, desktop, codex, pi and opencode uploaders adopt the shared builder over keeping their inline non-filtering join: the same reason, and a differing rule would make every real revoke look superseded.
- Shared module in the session layer (`session/cookie-auth.ts`) over `proxy/plugins/`: agents, cli and telemetry code must import it, and the proxy plugins already import from the session layer.
- `refreshNow()` returns the stored credentials and updates the refresher's snapshot over returning a boolean or leaving the snapshot alone: the re-sent request is served the new cookies at once, and replay stays possible later.
- `refreshNow()` as a separate method over a `force` flag on `refresh()`: keeps `refresh()`'s signature for its other consumers.
- Re-read failure falls back to the existing sign-in path over suppressing it: a genuine revoke must never be swallowed. The post-success cooldown delays a second browser rather than preventing it; accepted because an unreadable store means the new credentials are unusable.
- Superseded-request 401 carries its own "session was just renewed" text over reusing the "session expired" lead-in: the session is not expired.
- Superseded branch builds its 401 through a new small helper and leaves the old inline block alone over refactoring the block now: PR #720 edits it.
- One neutral post-success text covering a finished sign-in and a repeat rejection over a text claiming the sign-in fixed it: it is shown in both cases.
- "30 seconds" in the text derived from `COOLDOWN_MS` over a literal: the text follows the constant.
- Stale-marker clear skipped for API-key profiles over running it for all: a sign-in says nothing about an API key, and the no-retry rule stays as is.
- Any new writer of `headers['cookie']` must go through `buildCookieHeader` (an Open-risks line) over storing the built header in `context.metadata`: lighter, and `SSOAuthInterceptor` is the only writer today.
- Metrics writer asks an injected callback, set by each sender that knows its store, over reading the store inside `MetricsApiClient`: the client has no store key (provider, URL) and the session layer must not import the proxy layer.
- Callback built where the cookies are read, from the same reader, over one default inside `MetricsApiClient`/`MetricsSender`: the default would know only the API base URL and could re-read a different credential (hook: profile and provider override; desktop: one URL; daemon: its refresher), and a wrong answer hides a real revoke. The central part is `metrics-sync-processor.ts:187` and the two helpers, so five of the eight cookie sources (daemon, hook sync, codex, pi, opencode) need one helper call and no sender edit.
- No callback where the caller passed cookies in over comparing them with the store: there is no store the cookies came from, and a mismatch would hide a real revoke.

## Open risks

- Item 3 is a narrow guard: the marker in the reproduction has `detectedAt` newer than `succeededAt`; items 1, 2 and 5 prevent that case, not item 3. Item 3 covers a marker written between the sign-in's marker clear and its `succeededAt` stamp, or left by a failed clear, mainly when `refreshNow()` fails.
- A leftover marker that a real revoke re-marks before any gate pass keeps its old `detectedAt`, so the gate judges it stale and clears it. That pass lets the prompt through without a sign-in; the next failed metrics send writes a fresh marker and the following gate pass blocks and signs in. The delay is one cycle. The proxied agent signs in on its own redirect regardless.
- The staleness check compares wall clocks of two processes on one host; a clock stepped back across a sign-in can make a genuine marker look stale, with the same one-cycle outcome.
- A failed clear is invisible to the gate; the stale marker stays until the next pass retries (harmless: ignored each time). A marker written between the gate's re-read and its unlink is lost: one-cycle delay.
- A header differing only in cookie order counts as superseded; not expected, a rewrite carries new token values. Any new writer of `headers['cookie']` must use `buildCookieHeader`, else every real revoke takes the superseded branch and nothing converges.
- Store unreadable (timeout, keychain locked) after a finished sign-in: the redirect takes the sign-in path and one extra browser opens after the 30 s cooldown, the ticket's end state on a failed read.
- Metrics path: with every store-backed sender wired, a rejection landing after a sign-in is ignored only when the re-read succeeds in time and differs from what was sent; otherwise the writer marks as before. Senders with caller-supplied cookies (`HookProcessingConfig.cookies`) still mark. The OTLP forwarder keeps its own stale flag. During a real revoke each auth-failed send costs one unthrottled store read (in the daemon shared in-flight), bounded by the 2-minute tick and by the 10 s to 30 s send timeouts elsewhere.
- Switching session sync and the five other uploaders to the filtering builder drops store entries with an empty name or control characters from the sent header; such a header would have failed in `fetch` anyway.
- Lock and marker are global: another profile's sign-in can trigger one harmless extra re-read (item 1), suppress one metrics mark (item 5), or make the gate clear this profile's older marker (item 3).
- A real revoke within 30 s of a sign-in, or a sign-in by another profile, is still blocked by the post-success cooldown and gets the neutral text: truthful, but with no immediate remedy for up to 30 s.
- Whether agent clients actually retry the "just renewed" 401 is unverified; AC8b shows the 401 is rare (only for a request built before the sign-in). The user sees a re-send message at worst.
- Only the daemon path has the manual harness check (AC8d); the other senders are covered by unit and wiring cases only.
- The daemon is long-lived: the fix takes effect after a proxy daemon restart; codex, pi and opencode uploads run in the agent's own process and take it on the next agent start.
