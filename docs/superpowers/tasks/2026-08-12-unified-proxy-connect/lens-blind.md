- **Deprecated `connect desktop --vscode-claude-code` combination is silently dropped.** The old `desktop` subcommand carried `.option('--vscode-claude-code', ...)` and configured the VS Code Claude Code extension alongside Claude Desktop (index.ts old lines ~269, ~428-457). The rewritten `desktop` alias (index.ts new lines ~262-483) removes that option and `AliasConnectOptions` (lines 64-69) has no `vscodeClaudeCode` field. Any user/script running `codemie proxy connect desktop --vscode-claude-code` now gets an "unknown option" error — a regression of the deprecated surface the task asked to preserve. The wiring test even codifies the removal (`expect(hasFlag(desktop)).toBe(false)`, lines 1707-1708).

- **`state`/`config` are used after the try/catch relying solely on `printProxyError` being `never`/`process.exit`.** In `connectTargets` (connect-orchestrator.ts lines 1155-1211), `let state: DaemonState;` and `let config` are assigned only inside the try; the catch calls `printProxyError` (declared `: never`, lines 871-882) then falls through to `results.push(await runClaudeDesktop(state, ...))`. If `process.exit` is ever a no-op (test stubs, or a future refactor that returns instead of exiting), `state`/`config` are `undefined` and the per-target writers dereference `undefined.syncCodeMieUrl`/`.url`. Definite assignment here is a compile-time fiction backed only by process termination.

- **Standalone `--vscode-claude-code` now spawns a `telemetryMode: 'claude-desktop'` daemon.** `deriveDaemonIdentity` (lines 736-741) maps `vscodeClaudeCode` onto the claude-desktop identity. Previously this behavior only existed as an add-on to `connect desktop` (already in desktop mode). A user configuring ONLY the VS Code Claude Code extension will now have metrics/conversations synced under `claude-desktop` telemetry — plausibly mislabeled analytics even though no *new* telemetry value is introduced.

- **Combined `--claude-desktop --vscode` serves the BYOK client from a claude-desktop-identity daemon.** `deriveDaemonIdentity` collapses any set containing an Anthropic target to `claude-desktop` (lines 736-741), then `runVscodeByok` (lines 1058-1112) writes the BYOK config pointed at that same daemon. Whether one daemon spawned with `telemetryMode: 'claude-desktop'` actually serves the vscode-byok client path correctly is an unverified assumption — the old vscode flow always spawned with `clientType: 'vscode-byok'`.

- **Sequential separate invocations thrash the single daemon and cannot coexist.** With the strict matcher (lines 767-777) and one `DEFAULT_DAEMON_PORT`, running `connect --claude-desktop` then later `connect --vscode` derives a different identity, fails the match, and `ensureDaemon` (lines 959-968) calls `stopDaemon()` — tearing down the still-in-use Claude Desktop proxy. Users must use a single combined invocation; separate connects for different clients silently kill each other. This is a behavioral consequence of the reconciliation not surfaced to the user.

- **Strict matching now restarts (kills) a running desktop daemon on profile/project/targetUrl differences the old loose gate tolerated.** The comment (lines 762-766) states this replaces the loose `telemetryMode !== 'claude-desktop'` gate. Previously `connect desktop` reused ANY claude-desktop daemon; now a differing active profile/project/URL forces `stopDaemon()` + respawn (lines 959-968), potentially interrupting an in-use proxy that the user did not expect to be restarted.

- **Bare `codemie proxy connect` (no flags) is only tested at the orchestrator layer, not the CLI layer.** The "prints target list" path (lines 1139-1142) is exercised by calling `connectTargets({ targets: {} })` directly. Because `connect` has both an action handler and subcommands under `enablePositionalOptions()` (index.ts lines 232-259), whether Commander actually invokes the action on a bare `connect` (vs. erroring "missing command"/printing help) is unverified — the advertised no-arg UX could be dead.

- **`--profile <value>` parsing under `enablePositionalOptions()` is untested.** The wiring tests (connect-wiring.test.ts) only pass boolean flags. `enablePositionalOptions` changes how the first operand switches parsing; a value-bearing option like `--profile foo` before other flags is a distinct case that isn't covered, and the comment (index.ts lines 233-236) hand-waves the reuse behavior without a test asserting `--profile` reaches the unified action.

- **Existing diagnostic logs were removed, reducing observability.** The old desktop flow emitted `logger.info('[proxy] Resolved Claude Desktop proxy configuration', ...)` and `'[proxy] Claude Desktop proxy daemon is ready', ...)` (index.ts old lines ~341-387). `ensureDaemon` (lines 934-990) logs neither — the daemon-ready and resolved-config structured events are gone, hurting debuggability of the lifecycle this rewrite is centered on.

- **Skills sync now runs unconditionally on every desktop connect, including the healthy-reuse path.** In the old desktop flow, `syncRegisteredSkills`/`syncPluginSkills` ran only inside `if (!running)` (index.ts old lines ~354-357). The unified flow runs them before `ensureDaemon` on every invocation (lines 1181-1185), adding work/latency even when a matching healthy daemon is reused. Failures are swallowed by `Promise.allSettled`, so a broken sync is invisible.

- **Duplicated and potentially confusing failure output.** On a per-target failure each `runX` prints `chalk.yellow('  Could not configure ...')` (e.g. lines 1053, 1109, 1126) AND `printSummary` prints a red `✗ Label — error` line (lines 1005, gated at 1216). A single failing target therefore emits two different-colored failure lines; a careful reader may think two things failed.

- **`ensureDaemon` restart message is misleading for non-client mismatches.** Line 963 prints "Restarting proxy to match the requested client..." whenever `!matches`, but the mismatch may be profile/project/targetUrl rather than client type (matcher lines 771-776). The old code distinguished "in Claude Desktop mode" vs "in VS Code mode"; the generic message can misattribute the cause of a restart.

- **`allFailed` via `Array.every` is vacuously true on an empty array; rollback safety depends only on the early-return guard.** Lines 1213-1224: `results.every(r => !r.ok)` is `true` for `[]`. It is safe only because `hasAnyTarget` (lines 1139-1142) guarantees ≥1 result. A future change that dispatches nothing while `startedInThisRun` is true would silently roll back a freshly spawned daemon. Fragile invariant with no assertion.

- **New imports into index.ts (`daemonMatchesRequest`, `verifySsoCredentials`, `printProxyError`, `type RequestedDaemonConfig`) may be unused in the visible surface.** index.ts lines 33-40 import these from connect-orchestrator, but the `proxy start` body (elided at the `@@ ... 375 lines` hunk) is not shown. If any is not consumed there, the zero-warning lint policy fails. Cannot confirm from the diff.

- **Partial success returns exit code 1 while leaving a running daemon and partially-written configs.** Lines 1213-1224 set `process.exitCode = 1` on any failure but keep the daemon when not all failed. A caller/CI checking the exit code sees failure even though some clients were successfully configured and the proxy is live — an ambiguous contract worth confirming with product.
