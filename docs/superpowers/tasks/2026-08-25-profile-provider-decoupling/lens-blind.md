- The migration always writes an explicit `workspace` object — even an empty `{}` — onto any local config it touches (`return { ...config, profiles, workspace };`), but `resolveWorkspace()` treats *any defined* `workspace` (including `{}`) as a whole-object override that skips the global scope entirely. So any project whose local config gets migrated (regardless of whether its profiles ever carried a workspace-moving field) permanently loses fallback access to the global scope's `codeMieUrl`/`codeMieProject`/etc, unlike a freshly created local config from `initProjectConfig`, which correctly omits the `workspace` key when it would be empty (`...(Object.keys(this.removeUndefined(workspace)).length > 0 ? { workspace } : {})`). No test exercises the migrated-then-resolved path together — only the migration's own idempotency test and a manually-authored (non-migrated) "falls back to global" test, which never observes this interaction. — src/migrations/006-decouple-provider-workspace-config.migration.ts (migrate(), ~lines 387-428) vs src/utils/config.ts resolveWorkspace() (~lines 933-941) and initProjectConfig (~lines 1090-1100).

- `loadWithSources()` unconditionally tags the workspace layer with `source: 'project'`, even when `resolveWorkspace()` actually fell back to the *global* scope because the local scope has no `workspace` defined — mislabeling where a value came from in the `--show-sources` output. The updated test itself confirms this: only the global raw config sets `workspace`, yet `sources['codeMieUrl']?.source` is asserted to be `'project'`. — src/utils/config.ts hunk adding `{ data: workspace, source: 'project' }` (~lines 1130-1133); src/utils/__tests__/config-project-override.test.ts "loadWithSources reports workspace-resolved codeMieUrl with source 'project'".

- `ProfileDisplay.format()`/`formatStatus()` still fall back to `profile.codeMieUrl` (`workspaceCodeMieUrl ?? profile.codeMieUrl`), but this diff removes `codeMieUrl` from `ProviderProfile` entirely (moved to the new `WorkspaceConfig`). `ProfileInfo`'s `profile` type is not shown as updated anywhere in the diff, so this fallback either references a field that no longer exists on the type or is permanently dead code that can never resolve to anything. — src/cli/commands/profile/display.ts lines ~165 and ~201.

- The migration's active-profile-or-first-match heuristic (`hasMovingField` / `sourceEntry`) pulls *all* WORKSPACE_KEYS values from a single "winning" profile and silently discards the same keys from every other profile in the scope, even when those other profiles had their own distinct `hooks`, `metrics`, `plugins`, or `codeMieProject` values. There is no warning or log when a non-chosen profile's workspace-moving fields are dropped during this one-time, non-reversible migration. — src/migrations/006-decouple-provider-workspace-config.migration.ts, migrate() ~lines 394-422.

- `userEmail?: string;` is deleted from `ProviderProfile` (src/env/types.ts) but is not added to the new `WorkspaceConfig` interface and is not part of `WORKSPACE_KEYS` in either the migration or `ConfigLoader`. Existing persisted profiles that had `userEmail` set are neither migrated nor stripped — the value becomes an untyped, orphaned field on disk that diverges silently from the pre-existing top-level `MultiProviderConfig.userEmail`.

- `WORKSPACE_KEYS` is maintained as two independent literal arrays — one in src/migrations/006-decouple-provider-workspace-config.migration.ts and one as a private static in src/utils/config.ts — with a comment acknowledging the migration intentionally does not import ConfigLoader's list. Nothing enforces the two stay in sync; a future field added to one and not the other will silently mis-migrate or mis-split data.

- Workspace resolution now applies CodeMie-specific fields (`codeMieUrl`, `codeMieProject`, `codeMieIntegration`) to every active profile regardless of provider, with no gating on whether the provider is CodeMie/SSO-related. The updated test "switching the selected global profile does not drop workspace context" explicitly shows an `anthropic-subscription` profile receiving `codeMieProject: 'shared-proj'`, whereas the previous code only composed project-context fields for profiles that plausibly used them. — src/utils/config.ts load() workspace composition (~lines 913-919); src/utils/__tests__/config-project-override.test.ts same-named test.

- `listProfiles()` and `handleStatus()` now render a single resolved `workspace.codeMieUrl` for every listed profile (`ProfileDisplay.formatList(profiles, workspace.codeMieUrl)`), even though the listed profiles can span both local and global scopes (when `hasLocal` is true) and different providers. Profiles that don't use CodeMie at all will now display the same workspace URL as CodeMie/SSO profiles, and any per-profile URL distinction that existed before this change is gone. — src/cli/commands/profile/index.ts ~lines 213-221 and ~229-233.
