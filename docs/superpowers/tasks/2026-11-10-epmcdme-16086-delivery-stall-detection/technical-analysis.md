## 1. Original Context

EPMCDME-16086 follow-up: "silent stall" gap in analytics delivery health.

Ticket EPMCDME-16086 ("codemie proxy status reports healthy while analytics forwarding is stopped") was implemented and shipped (commit d97742c, docs/superpowers/tasks/2026-11-05-epmcdme-16086-analytics-status/). QA verified it as "partially fixed": when a session has NEVER completed classification yet (fresh machine/profile/reinstall) AND the analytics backend is unreachable from the very first classification-policy probe, `codemie proxy status` / `codemie proxy analytics status` keep reporting `Analytics: healthy` / `Delivery: healthy` for the whole outage (pendingBytes never drains, no progress), because the existing `send_failed` reason only fires after a real POST attempt gets an unacknowledged response — and in this scenario no POST is ever attempted (the forwarder fails closed before reaching `send()`, per `evidence-send.ts` / `tick-processor.ts` / `classification.ts`). This was an explicit non-goal at spec time ("Last-successful-delivery time, and detecting a stall that leaves no failure record") after 3 rounds of HITL spec review where an earlier `not_delivered`/`undeliveredSince` design was tried and reverted (see decisions.jsonl rounds 1-3 in docs/superpowers/tasks/2026-11-05-epmcdme-16086-analytics-status/) — the detailed rationale for the revert was not preserved.

Prior analysis already done this session (verify, don't re-derive from scratch):
- The gate that blocks sending before classification succeeds lives in `src/providers/plugins/sso/proxy/plugins/otlp-spool/tick-processor.ts` (`evaluateSessionEvidence` in `session-project.ts`) and sets `status.holds.session = { reason, since }` — this already has a persisted first-held timestamp, reused today only for `identity_mismatch` (`analytics_endpoint_mismatch` reason) in `delivery-summary.ts`.
- A naive "any `status.holds.session` + pendingBytes>0 = unhealthy" would create false positives for by-design holds unrelated to backend/network trouble: `personal_not_forwardable` (personal-data privacy hold), `publication_stopped` (explicit consent-revoked stop), `project_conflict`, `otlp_unparseable`, `otlp_entry_too_large`, `evidence_capacity` (local-only), and possibly `organization_encoding_unsupported`/`publication_contract_unavailable` (could mean "backend/org on an older version", not "something is broken").
- Separately (already-shipped, pre-existing behavior): backend 503 responses with reasons `project_analytics_not_enabled`, `personal_storage_unsupported`, `destination_unsupported`, `publication_contract_unavailable` already get recorded as `destination_hold` in `delivery-state.ts` → counted toward the existing `sendFailed`/`send_failed` reason. Needs independent verification whether this is already a false-positive source today.
- `stamp_pending` is also the NORMAL transient state every brand-new session passes through briefly even when the backend is healthy.

Task: produce a real, evidence-based analysis of which specific local hold/reason states genuinely mean "we cannot reach or get a useful answer from the CodeMie analytics backend to classify/deliver this session" vs. which are legitimate, by-design, backend-configured, or local-only states that must NOT be reported as unhealthy — grounded in actual code, not guesswork. (Full trace list and extra evidence sources: see run inputs; all were read — see Sections 2 and 8.)

## 2. Codebase Findings

### Existing Implementations

**Purpose: decide, per session, whether local-classification evidence allows a send at all (session-level hold).**
- `evaluateSessionEvidence` (`session-project.ts:97-115`) is the single pure decision point. Order of checks: `publication_stopped` (explicit stop marker) → `stamp_invalid` → `send_evidence` (new-contract, `negotiate_publication`) → `publication_contract_unavailable` (new-contract record whose `funding_route` is set but `contractAdvertised === false`) → `personal_not_forwardable`/legacy (capability `legacy`) → `send_evidence` (valid record, any other capability) → legacy send (has hooks or pre-epoch) → `stamp_pending` (nothing yet). Consumers: `tick-processor.ts:102-115` (`applySessionEvidenceLocked`), read by `evaluateProjectPolicy` (`session-project.ts:262`, any `status.holds.session` blocks both streams), by `delivery-summary.ts:30` (only `analytics_endpoint_mismatch` is read today), and by `expireCarriedAgeLocked` (`delivery-state.ts:62-64`, uses the hold reason to pick the loss reason for handed-over bytes).
- `holdOrLose` (`session-project.ts:54-62`) is the shared retention clock: every `HoldReason` (including `publication_contract_unavailable` and `publication_stopped`) is bounded by `heldRetentionMs()` (`spool-config.ts:48-50`, default 24h via `OTLP_HELD_RETENTION_MINUTES`), measured from the persisted `since`.

**Purpose: decide, per session, whether the backend's classification (org/personal/corporate) allows a send (`classifySession`, `classification.ts:74-116`).**
- Reads/writes the verdict store (`verdict-store.ts`); with no usable policy (`state.policy === null`, i.e. backend never answered usefully) a sticky verdict already recorded as `personal` is held `personal_not_forwardable` only if the previous capability does not allow a full-evidence send; otherwise (no sticky verdict yet — the exact fresh-install case) nothing here holds, and `decide()` is consulted.
- `decide(result, consumer)` (`classify.ts:57-59`): "Default (undefined): everything is forwarded" — no built-in backend-reachability withhold; `classification_unresolved` only fires when a `Consumer` callback is injected via `setClassificationConsumer` (the "#711 seam"), not by default.
- `organizationSendable` (`org-encoding.ts:49-51`): with `state.policy` null, `encodings` is `undefined`; `organizationSendable` returns `true` whenever the organization name doesn't need encoding (the common ASCII case) — so a session with a plain-ASCII organization and no sticky verdict is **not** held for `organization_encoding_unsupported` just because the backend is unreachable; it proceeds to `{action:'send'}` and would be forwarded over the network (and would then fail as an ordinary network error, feeding `send_failed` via the mechanism below, not stalling silently).

**Purpose: decide capability of the backend (evidence-capable / legacy / unconfirmed) — `policy-cache.ts`.**
- `probe()` (`policy-cache.ts:147-168`) returns `{kind:'unknown'}` on any network error, timeout, non-JSON body, or non-200/404 status; `{kind:'legacy'}` only on an **authenticated** 404; `{kind:'ok', policy}` on a valid 200. `refreshPolicy` (`:171-205`) persists `capability: 'unknown'` only while no prior probe ever returned `'evidence'` (`prev?.capability === 'evidence' ? 'evidence' : 'unknown'`, line 194) — i.e. **capability is sticky once confirmed evidence-capable**, and `backoffUntil` is re-armed (5 min, `BACKOFF_MS`) on every unknown outcome. This `capability: 'unknown'`-with-no-prior-success state is the closest thing in the code to "we have never gotten a useful answer from the backend," and it is **not currently read by any health/status consumer** — it lives only in the per-namespace `*.policy.json` cache file (`policy-cache.ts:85`), never copied into `status.holds` or `DeliveryHealth`.
- `advertisesContract` (`policy-cache.ts:67-68`) and `getPolicyState`'s `publicationContracts` (`:129`, set only when `capability === 'evidence'`) are what feed `contractAdvertised` in `evaluateSessionEvidence`. Both an **unreachable backend** (capability stuck `unknown`) and a **reachable-but-old backend** (capability `evidence`, policy fetched fine, but `publication_contracts` doesn't list `"1"`) make `contractAdvertised === false` — same downstream `publication_contract_unavailable` hold, same `status.holds.session` shape. The two cases are distinguished only by a one-shot, write-once stop-marker **notice** text (not re-read on later ticks): `tick-processor.ts:136-143` writes `hold_contract_unavailable` (authoritative: policy fetched, just doesn't advertise it) vs `hold_state_unknown` (capability still `unknown`) — confirmed by the test named exactly for this case: `tick-processor.test.ts:620` *"capability unknown (backend unreachable): still held and fail closed, but the notice says it could not be confirmed"*.
- **The self-resolving loop at the retention bound** (`tick-processor.ts:146-150`, test `tick-processor.test.ts:633`): once a `publication_contract_unavailable` hold reaches 24h, `tryStop(key, 'hold_expired', ...)` writes a *permanent* stop marker; `status.holds.session` is cleared and the backlog is recorded as `lastLoss` (reason `publication_contract_unavailable`) in the same tick. On the *next* tick `isStopped(key)` is now true, so `evaluateSessionEvidence` immediately re-enters `hold('publication_stopped')` with a *fresh* `since`. New bytes arriving after that point accumulate under `publication_stopped`, which is itself subject to the same 24h retention and will "lose"/re-hold again. So `publication_stopped` is **not** purely the by-design, consent-revoked, leave-it-alone state the prior analysis assumed — it is also the resting state a genuinely-stalled new-contract session cycles into after 24h, repeating indefinitely while the backend stays unreachable.

**Purpose: detect delivery failure for `codemie proxy status`/`proxy analytics status` ("healthy"/"unhealthy").**
- `collectDeliveryHealth` (`src/cli/commands/proxy/delivery-health.ts:36-66`), shipped by EPMCDME-16086. Precedence: `credentials_expired` → `auth_rejected` → `identity_mismatch` (`spool.mismatchHeld`, i.e. `holds.session.reason === 'analytics_endpoint_mismatch'`) → `send_failed` (`spool.sendFailed`). No other `HoldReason` is read.
- `summarizeSpoolDelivery`/`summarizeSession` (`delivery-summary.ts:21-55`) compute `sendFailed` from `liveDelivery` (`delivery-state.ts:18-26`) across all streams of all sessions — a **status.delivery record**, not a `status.holds.session` record. `status.delivery[stream]` is populated only by `noteDeliveryFailure` (`delivery-state.ts:140-176`), called from the forwarder only after an actual HTTP response (or request failure) is classified by `deliveryFailureOf` (`:183-192`). A session that never reaches `send()` (held in `status.holds.session`) never gets a `status.delivery` entry, so `sendFailed` stays `false` for it — this is the exact mechanism of the shipped gap.

**Confirmed, pre-existing false positive in `send_failed` (backend-configured, by-design 503s already counted as failures today).** Traced end to end: backend `cli_analytics_project_gate.py` (`C:\Repositories\codemie`) raises `503 project_analytics_not_enabled` when a bound project exists but its `cli_analytics_enabled` flag is off (admin toggle, line 561), `503 personal_storage_unsupported` for an excluded user/subscription type (N0 regime, no DB lookup), `503 destination_unsupported` for a project name that can't be echoed as a header value, and `503 publication_contract_unavailable` when the operator setting `CLI_ANALYTICS_PUBLICATION_CONTRACTS_ENABLED` is off (rollout pause) or the contract isn't advertised — the backend spec (`docs/superpowers/tasks/2026-11-04-subscription-analytics-backend-capability/spec.md`, wire-contract table) explicitly marks all four as `disposition: hold` ("bounded by the CLI retention window, then suspend... the CLI shows a notice at the FIRST hold"), as opposed to `personal_destination_unavailable`/`default_project_unavailable`/storage errors which are `disposition: retry`. On the CLI side, `HOLD_503_REASONS` (`response.ts:33-35`) lists exactly the backend's four "hold" reasons, and `decodeResponse` (`response.ts:181-186`) marks them `hold: true`; `deliveryFailureOf` (`delivery-state.ts:183-192`) then maps **any** `hold && detail` response to `DeliveryLossReason: 'destination_hold'` — the same bucket as a genuine `retry`-disposition failure — and `noteDeliveryFailure` records it as a live `status.delivery` entry. `summarizeSession`'s `liveDelivery` check (`delivery-summary.ts:31`) does not distinguish `destination_hold` from any other delivery-failure reason, so a project with analytics simply not enabled for it (admin hasn't flipped the flag — nothing broken) shows `Delivery: unhealthy (sending to analytics failed on this machine)` for as long as new bytes keep arriving and failing the same way, i.e. indefinitely. This confirms the open question in the prior analysis.

### Decisions Already in the Code

- `HoldReason` is a flat union (`session-project.ts:6-22`) with no tag distinguishing "local/by-design" from "backend-dependent" holds; any consumer that wants that distinction must classify the 14 reason strings itself (as `delivery-health.ts` and the prior analysis already attempt, incompletely).
- `Hold.since` (`session-project.ts:47-51`) is "kept across reason changes and restarts" — the one piece of state the task is directed to reuse. It is per-session, not global: a machine-wide "oldest unresolved hold" view would need to scan every session's `status.holds.session.since`, as `summarizeSpoolDelivery` already does for `pendingBytes`/`mismatchHeld`/`sendFailed`.
- Backend capability (`unknown` vs `legacy` vs `evidence`) is cached **per namespace** in a separate file (`policy-cache.ts:85`, keyed by `sha256(api_identity, owner_hash, profile)`), not per session and not inside `status`. Reusing it from a health collector means reading a second on-disk cache the shipped collector does not read today, not reusing `status.holds.session.since` as directed — i.e. the two existing signals (`capability` and `status.holds.session.since`) answer different parts of "is the backend actually unreachable" and neither alone resolves it for `publication_contract_unavailable`/`organization_encoding_unsupported`.
- The backend's own hold/retry split (confirmed in Section "Existing Implementations" above) is the authoritative model the CLI's `HOLD_503_REASONS` already mirrors for *delivery*-level 503s; no equivalent split exists yet for *session*-level `HoldReason`s (stamp/classification holds), which is exactly where the gap QA found lives.
- `publication_contract_unavailable`'s self-resolving 24h → `publication_stopped` transition (`tick-processor.ts:146-150`) is a recorded, deliberate choice (not an oversight): a hold that cannot be converted to a stop (write failure) stays held and retries; one that can, converts, so the spool never grows unbounded. The reason for *this* design is in code/tests, not in the reverted `not_delivered` decisions.jsonl entries (round-3 rationale was not preserved, confirmed absent from `docs/superpowers/tasks/2026-11-05-epmcdme-16086-analytics-status/decisions.jsonl`).

- "`personal_not_forwardable`, `publication_stopped`, `project_conflict`, `otlp_unparseable`, `otlp_entry_too_large`, `evidence_capacity` are by-design/local-only" — **mostly holds, with one exception**: `personal_not_forwardable`, `project_conflict`, `otlp_unparseable`, `otlp_entry_too_large`, `evidence_capacity` are local/by-design as stated (no network dependency found in their triggering code: `evidence_capacity` is a local record-store cap, `otlp_unparseable`/`otlp_entry_too_large` are local parse checks, `project_conflict` is a local name-conflict). `publication_stopped` **is contradicted** for one path: see "self-resolving loop" above — it also serves as the resting state of an expired `publication_contract_unavailable` hold, so a backend that has been unreachable for >24h now also presents as `publication_stopped`, which the task's framing treats as purely "explicit consent-revoked stop."
- "`organization_encoding_unsupported`/`publication_contract_unavailable` could mean backend/org on an older version, not broken" — **holds for `organization_encoding_unsupported`** (requires a fetched `state.policy`, i.e. a reachable backend, to even be reached by `classifySession`'s final check) but **only partially holds for `publication_contract_unavailable`**: the backend confirms this 503 reason is also used for a deliberate operator pause (`CLI_ANALYTICS_PUBLICATION_CONTRACTS_ENABLED=false`), genuinely "not broken" — but the *local* CLI hold of the same name is also reached when capability is `unknown` because the backend was never reachable at all (see "capability" bullet above), which the task's own framing already flags as the open question; code confirms both are real, coexisting causes of the identical `status.holds.session.reason`.
- "destination_hold 503 reasons already feed sendFailed today — needs independent verification" — **contradicted toward "worse than suspected"**: confirmed as a real, already-shipped false positive (see "Confirmed, pre-existing false positive" above), not merely a theoretical risk.

- `HOLD_REASONS`/`LOSS_REASONS` (`session-project.ts:6-45`): read wherever a `HoldReason` is pattern-matched; `LOSS_REASONS` is derived from `HOLD_REASONS` automatically, so adding a hold reason (if a fix did that) also adds a loss reason with no separate registration — found by searching every `case`/comparison against these arrays; no additional unlisted consumer found.

### Integration Points

- Internal: `tick-processor.ts` orchestrates `session-project.ts` → `classification.ts` → `publication-mode.ts` → `forwarder.ts`/`evidence-send.ts`; `delivery-health.ts` depends only on `delivery-summary.ts` + `auth-state.ts` + `sso.auth-gate.ts`, not on `policy-cache.ts` or `classification.ts` today.
- External: backend `GET /v1/analytics/cli-analytics/classification-policy` (policy-cache.ts probe) and the OTLP/hooks ingest POSTs (forwarder.ts) are the only two network calls in this path; both target the same resolved `baseUrl` (`resolveAnalyticsEndpoint`, `classification.ts:132-160`), so "classification-policy unreachable" and "ingest unreachable" are almost always the same outage.

### Patterns and Conventions

- Pure-decision functions (`evaluateSessionEvidence`, `holdOrLose`, `classify`, `decide`) take all inputs explicitly and return a tagged union; side effects (status writes, notices, stop markers) happen only in the `tick-processor.ts` caller, under the session lock. Any fix should keep this split.
- Every reason-keyed map in this area is typed `Record<ReasonUnion, ...>` (`DELIVERY_REASONS`, label maps) specifically so an unhandled new code fails to compile (documented in the shipped spec, AC6).

## 6. Risk Indicators

- `publication_stopped` is not purely a by-design, consent-revoked, leave-alone state as the prior analysis assumed — it is also the resting state a genuinely-stalled `publication_contract_unavailable` session cycles into every 24h (`tick-processor.ts:146-150`); a fix that excludes `publication_stopped` wholesale from "unhealthy" would silently re-introduce the exact stall it is meant to catch, just one hop later (see Section 2, "self-resolving loop").
- `publication_contract_unavailable` and `organization_encoding_unsupported` are reached by two structurally different causes each (reachable-but-old-backend vs. never-reachable-backend) that are *not* distinguishable from `status.holds.session` alone; the only existing signal that tells them apart (`policy.capability`) lives in a separate per-namespace file the shipped health collector does not read (Section 2, "Decisions Already in the Code").
- Today's shipped `send_failed` already double-counts backend-configured, by-design 503 holds (`project_analytics_not_enabled`, `personal_storage_unsupported`, `destination_unsupported`, `publication_contract_unavailable` as *response*-level `destination_hold`) as delivery failures — a pre-existing false-positive, confirmed against the backend's own `hold`/`retry` disposition model, independent of this task's silent-stall scope.
- Round-3's revert of `not_delivered`/`undeliveredSince` carries no preserved rationale beyond the one-line decision log entry; whatever drove that revert is not discoverable from this repository and should be asked of the user rather than re-derived.
- Speculative: because the backend's own 503 contract already models `hold` vs `retry` dispositions per reason, and the CLI's `HOLD_503_REASONS` already mirrors it at the delivery layer, a parallel split at the session-hold layer (marking certain `HoldReason`s as "backend-confirmed" vs "backend-unconfirmed," using the already-persisted `since`) is one shape a fix could take — this is a design option, not a finding.

## 7. Summary for Complexity Assessment

The change sits entirely inside the existing OTLP-spool classification/delivery layer (`src/providers/plugins/sso/proxy/plugins/otlp-spool/`) and its CLI presentation consumer (`src/cli/commands/proxy/delivery-health.ts`), the same files the already-shipped EPMCDME-16086 change touched. No new architectural layer, external service, or schema is implicated; the relevant state is already persisted (`status.holds.session.{reason,since}`, the per-namespace policy-cache file's `capability`). The core technical difficulty is not file count but disambiguation: several `HoldReason`s (`publication_contract_unavailable`, `organization_encoding_unsupported`) are reached by both a genuinely-unreachable-backend path and a legitimately-old-backend/operator-paused path with identical persisted shape, and one state (`publication_stopped`) silently absorbs an expired stall after 24h, so a shallow reason-allowlist risks either missing the real stall or mis-flagging healthy, by-design states.

Test coverage for the exact silent-stall precondition already exists at the unit level (`tick-processor.test.ts:620`, `:633`) but has no counterpart at the health-collector/CLI-presentation level (`delivery-summary.test.ts`, `delivery-health.test.ts`) — that gap is squarely what QA found. The backend repository (`C:\Repositories\codemie`) independently confirms the authoritative meaning of every ambiguous 503 reason and its hold/retry disposition, which materially changes one assumption in the original analysis (`publication_stopped` is not purely by-design) and resolves one of its open questions (the existing `send_failed` false-positive on backend-configured 503 holds is confirmed, not hypothetical). Given the prior spec's three rounds of HITL revision on a closely related design and the two genuinely ambiguous reason codes, this follow-up carries moderate design risk despite its small, well-scoped file surface.
