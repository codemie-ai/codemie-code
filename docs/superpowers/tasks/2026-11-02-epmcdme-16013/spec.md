# EPMCDME-16013: Story mention detection must not treat UUID fragments and tech tokens as tickets

## Problem

The lowest story tier ("mention") takes the first `TICKET_RE` match in the prompt (`src/agents/core/story-resolver.ts:106-113`, `src/agents/core/ticket-parser.ts:13`). The regex accepts any `letters/digits-digits`, case-insensitive, so `agent.prompt.submit` gets a wrong `story_id` with `story_source=mention` for UUID fragments (`a43e-20`, `df51-48`), `SHA-256`, `UTF-8`, `GPT-4`, `X86-64`.

All three OTLP adapters (claude-code-otlp, copilot-chat-otlp, copilot-cli-otlp) reach this through `OtlpAgentAdapter.resolveCommonFields -> resolveRepoFields -> resolveStoryFor`; there is no duplicate resolver and the managed `copilot-cli` plugin has no story logic (technical-analysis section 2). The fix therefore lives once, in the shared parser, and covers every adapter without per-agent code.

The goal is that the classes named below yield no story. The set of non-ticket `name-number` tokens is open-ended and this fix does not close it. It closes UUID-shaped tokens structurally and the enumerated token families by a closed, extendable data list, and it leaves the rest as accepted residual (Non-goals). In particular, case-insensitive matching is kept (requester decision), so lower-case tokens off the list (`us-east-1`, `node-20`, `qwen3-8b`) still resolve as a mention unless the prompt also holds an upper-case key, which then wins (rule 3), and a bare two-segment fragment such as `a43e-20` typed on its own still does; only fragments inside a recognisable UUID are dropped.

## Approach

Filter candidates inside `extractTicketMentions` (`ticket-parser.ts:32`), the single function behind the mention tier, the branch tier and the claude-only `ticket_mentions` field. `TICKET_RE` stays exported and unchanged, documented as the raw candidate shape. Each regex match is a candidate and is dropped when rule 1 or 2 applies; among the survivors the first wins, except that the mention tier's story pick prefers an upper-case key (rule 3). So `sha-256 then EPMCDME-1` yields `EPMCDME-1`. Dedupe, upper-casing, limit and fresh-RegExp-per-call behavior are unchanged. Rules 1 and 2 live in one predicate next to `TICKET_RE`, with the segment lengths and the key list as named constants; both read the dash-joined runs from one tokenizer whose join set is a single constant (the digit-bounded `.` of rule 2(b) is a flag of that tokenizer; the plan may give it to rule 1 as well only if running AC1-AC3 and AC10-AC11 shows no outcome differs). The rule has its own segment-layout UUID check and does not reuse the whole-string UUID patterns at `src/utils/paths.ts:252` and `src/cli/commands/sdk/assistant-builder/conversations.ts:38` because partial pastes, glued words and numeric suffixes are in scope (AC2, AC3) and a later "simplification" to those patterns would break them; the `extractTicketMentions` doc comment says so.

`extractTicketMentions` gains an options object, `extractTicketMentions(text, limit, { source, preferUpperCase })`, with `source: 'prompt' | 'branch'` (default `'prompt'`) and `preferUpperCase: boolean` (default `false`); both defaults are stated in the doc comment. `resolveMentionStory` passes `preferUpperCase: true`; `parsePromptFields` uses the defaults, so `ticket_mentions` keeps first-seen order and full inclusion; `resolveBranchStory` (`story-resolver.ts:80`) passes `'branch'`. The base-class re-run at `OtlpAgentAdapter.ts:311` goes through `resolveBranchStory`, so it needs no change.

1. **UUID-shape rule (both sources).** A candidate has a key segment (the text before the dash) and a number segment (the dash-separated segment starting with its digits). A segment is a maximal `[A-Za-z0-9]+`; segments are joined by a single `-`, and space, `_`, `.`, `/`, `=`, `:` or `--` end the run. For each of the key and number segments that is all-hex (`[0-9a-f]+`, any case), take the maximal run of consecutive all-hex segments containing it. Drop the candidate when that run holds a window of three or more consecutive segments, **including that key or number segment**, whose lengths equal consecutive groups of the UUID layout 8-4-4-4-12 and where at least one is the 8 or the 12 group. Also drop the candidate when its key segment is itself exactly 12 hex characters (the UUID tail group). The key segment may be non-hex, so a word glued to a pasted UUID (`session-<uuid>`, `agent-<uuid>`, `<uuid>-v2`) does not defeat the rule; a suffix after the UUID (`<uuid>-2`, `session-<uuid>-123`) no longer lets the tail group through; and a real key with a hex-looking suffix (`ABC-1234-added`, `feature/ABC-1234-fade`, `ABC-123-add`, `fix-ABC-123`) does not match the layout and is kept. A window spans at most five segments, so reading four segments on each side of the key or number segment gives the same answer as reading the whole run; the read is bounded that way.
2. **Known non-ticket prefix rule (prompt source only).** A candidate is dropped when either condition holds; both use one named constant in `src/agents/core/ticket-parser.ts`, next to `TICKET_RE`, marked as a closed, extendable data list: standards and algorithms `SHA, UTF, ISO, CVE, CWE, COVID, X86, X64, AES, RSA, MD`; protocols `HTTP, TLS`; model and vendor families `GPT, CHATGPT, CODEX, CLAUDE, GEMINI, GROK, LLAMA, MISTRAL, DEEPSEEK, QWEN, GLM, KIMI, SONNET, OPUS, HAIKU` (the family tokens are the first segments of the model ids `src/utils/pricing.json` prices, plus the ticket's own). The list stays closed: it is extended by adding one entry to that constant plus one assertion in `ticket-parser.test.ts` and shipping a release, and its comment tells whoever adds a model family to `pricing.json` to add the family's first segment here. The O-series (`O1`, `O3`, `O4`) is left off on purpose (Decisions).
   - (a) Key condition: the candidate's whole key part (text before the dash, case-insensitive, exact match, so `LLAMA3` is not `LLAMA`) is on the list, wherever it sits in its run (`my-sha-256` is dropped).
   - (b) Leading-token condition: the **prompt run** containing the candidate has a first segment on the list (same exact, case-insensitive match). Then every candidate inside that run is dropped, not only the one whose key is listed, so the version and variant tail of a full model id does not become the story (`gpt-4o-mini-2024-07-18` would otherwise leave `MINI-2024`, `gemini-2.0-flash-001` would leave `FLASH-001`, `grok-code-fast-1` would leave `FAST-1`). The prompt run is the UUID rule's run (maximal `[A-Za-z0-9]+` segments joined by a single `-`; space, `_`, `/`, `=`, `:`, `--` and any other delimiter end it) with one addition: a `.` between two digits also joins (`gemini-2.0-flash-001`, `claude-3.5-sonnet`); every other `.` ends the run. The digit-dot join is the spec author's choice, confirmed by the requester. Run starts are found in a single pass over the text (or a bounded read), so the cost stays linear in the text length.

   The rule applies to the mention tier and `ticket_mentions`, never to branch names: a branch is typed deliberately, the ticket shows no branch defect, and a team whose Jira project is one of these keys would otherwise lose its story on every event of the branch. No listed token is all-hex (each contains a non-hex letter), so (b) never collides with the UUID rule's 12-hex key check; where both apply, both drop the candidate.
3. **Upper-case preference (prompt source, story pick only).** After rules 1 and 2, when the surviving candidates include both upper-case-key and lower-case-key ones, a call with `preferUpperCase` returns the upper-case ones first and then the lower-case ones, each group in first-seen order, before the limit is applied; so the mention tier (limit 1) takes the first upper-case survivor, and with no upper-case survivor the first lower-case survivor wins as today (`check epmcdme-15301` still resolves). An upper-case key is a key part (text before the dash, as written in the prompt) with no lower-case letter: digits are ignored and the key always begins with a letter, so `EPMCDME`, `A1`, `E2E` are upper-case and `node`, `Node`, `a1` are not (mixed case counts as lower-case). Dedupe stays by upper-cased id, and an id counts as upper-case when any surviving occurrence is written upper-case (`abc-9 ... ABC-9`). It is a single pass over the matches, linear in the text length. `ticket_mentions` does not use it, because `ticket-parser.test.ts:7` and `:43` assert first-seen order for that field; the consequence is that `story_id` may differ from `ticket_mentions[0]` (`use node-20 for EPMCDME-15301` gives story `EPMCDME-15301` and field `['NODE-20','EPMCDME-15301']`). The branch tier does not use it either: branch names are conventionally lower-case (`feature/epmcdme-16013-x`) and the ticket shows no branch defect.

The marker tier (`story: X`) is untouched: an explicit marker is the user's deliberate statement, and it is also the remedy for a mention-tier loss, since the mention tier exists on prompt events only.

## Non-goals

- No project-key allowlist and no new config, env var or file; short synthetic keys stay valid.
- No change to `TICKET_RE`, `MARKER_RE`, tier order, `story_source` values, or any adapter file.
- No mention-tier upper-case-only key shape (lower-case keys still resolve; rule 3 only ranks them behind upper-case ones) and no digit-tail-stripped key comparison (requester decisions, see Decisions): the matching rule stays case-insensitive and exact-key.
- Accepted residual false positives, by decision: lower-case tokens not on the list resolve as a mention when the prompt holds no upper-case key (regions `us-east-1`, runtimes `node-20`, `java-17`, hosts `ip-10-0-0-1`, version-glued model names `qwen3-8b`, `llama3-8b`, `qwen2.5-coder-32b` (`CODER-32`), pod names `pod-name-7d9f8c6b5d`); a real key typed lower-case after such noise loses to it (`node-20 then epmcdme-15301`), and upper-case off-list noise typed before a real key wins (`RFC-2616 for EPMCDME-15301`, `E2E-1`), the `story:` marker recovering the story; a listed token that is not the first segment of its dash-joined run keeps only condition (a), so `openai-gpt-4o-mini-2024-07-18` still yields `MINI-2024`; O-series model ids (`o1-mini-2024-09-12` yields `MINI-2024`); other `name-number` tokens (`PR-123`, `e2e-1`, `v1-2`, `RFC-2616`, `abc-123` in free prose); two-segment hex-looking fragments typed alone (`a43e-20`, `a43e-20c8e1f66c87`); a middle UUID piece of three 4-character groups; UUIDs split by whitespace; and `story: sha-256` (explicit marker). The list is closed and extendable: adding a token is a one-line edit plus a release, and older installed hooks keep the old behaviour.
- Branch tier: prefix tokens in branch names keep resolving as today (`feature/GPT-4-support` yields `GPT-4`), and branches are not ranked by case; not changed here.
- Accepted residual loss: a real Jira project whose key is on the prefix list is not detected by the mention tier or `ticket_mentions`; the `story:` marker, the branch or the explicit tier recovers the story, nothing recovers `ticket_mentions`. A real key that is a 12-hex-character word, or is followed by a segment of 8 hex characters and two 4-character hex words (`ABC-12345678-dead-beef`), is dropped as UUID-shaped.
- Accepted residual loss, by requester decision (answers AR-6): a real key glued by a dash to a leading segment on the prefix list (`gpt-4o-EPMCDME-15301`, `sha-EPMCDME-15301`) is not detected by the mention tier or `ticket_mentions`, because the whole dash-joined run is dropped. The same key separated by a space or any other delimiter (`gpt-4o EPMCDME-15301`, `gpt-4o, EPMCDME-15301`, `gpt-4o_EPMCDME-15301`, `gpt-4o/EPMCDME-15301`) is still detected, and the `story:` marker recovers the story in the glued case.
- Wrong `story_id` rows already stored in analytics and older hooks that keep emitting them: not corrected here, no owner assigned in this repo (backend side).
- No cross-turn story memory, no backend or spool change, no commit of any changes by the agent, `.codemie/codemie-cli.config.json` untouched.
- Stage 1.1 spec/plan files under `docs/superpowers/tasks/2026-10-01-epmcdme-15301-stage-1-1/` are historical and not edited; the live architecture doc carries the supersession note. The technical analysis is not edited either.

## Decisions

- Self-contained heuristic (UUID-shape structure plus a named prefix list) over a known-project-key allowlist: no key source exists and existing tests assert short synthetic keys as valid.
- Fix in shared `extractTicketMentions` over a mention-tier-only filter: one definition for the mention tier, branch tier and `ticket_mentions`, and every OTLP adapter is covered with no per-agent patch.
- Skip a rejected candidate and keep scanning over giving up on the first match: a real key later in the prompt still wins.
- Keep case-insensitive prompt matching with the closed prefix list over an upper-case-only prompt key shape or a digit-tail-stripped comparison: lower-case non-ticket tokens off the list stay accepted residual, and the requester comments on the Jira bug himself — user, answers AR-4
- Prefer the first upper-case-key survivor in the mention tier's story pick over first-seen order alone, and a lone lower-case survivor still resolves: `use node-20 for EPMCDME-15301` then gives the real key — user, answers AR-8
- Upper-case key defined as a key part with no lower-case letter, digits ignored, over also counting mixed case (`Node-20`) as upper-case: a capitalised word is prose, a ticket key is written in capitals.
- An id counts as upper-case when any surviving occurrence is written upper-case over judging only its first occurrence: `abc-9 ... ABC-9` is a deliberate key, and dedupe stays by upper-cased id.
- Ranking as the `preferUpperCase` option used by the mention tier only, `ticket_mentions` keeping first-seen order and full inclusion, over reordering the field: `ticket-parser.test.ts:7` and `:43` assert first-seen order, and the field is a record of what was written; the cost is that `story_id` may differ from `ticket_mentions[0]`.
- Branch tier not ranked by case over applying rule 3 to it: branch names are conventionally lower-case and the ticket shows no branch defect.
- UUID-shape rule judged on the hex run containing the candidate's key or number segment, matched against the 8-4-4-4-12 layout, over the number segment only: a letter-led UUID tail followed by `-<digits>` is otherwise taken as a ticket — user, answers AR-5
- A key segment of exactly 12 hex characters dropped on its own over requiring a three-segment window: covers the bare tail `a43e8c1f66c8-123`; a real 12-character all-hex key is not plausible — user, answers AR-5
- UUID-shape rule judged on the hex run over thresholds on the whole dash-run (3 segments, two of 4+ chars): the old unit missed `session-<uuid>` and dropped `ABC-1234-added`.
- UUID window must contain an 8 or 12 group over accepting any three 4-character groups: keeps `ABC-1234-fade-beef`-like real keys, at the cost of leaving a bare middle UUID piece as residual.
- Prefix list widened with model names and protocol tokens (`CLAUDE, GEMINI, LLAMA, QWEN, GLM, SONNET, OPUS, HAIKU, HTTP, TLS, MD`) over the narrow list from the ticket plus siblings: model names are the likeliest `name-digit` tokens in prompts to an AI-agent CLI (inference, not measured).
- `GROK, CODEX, CHATGPT, MISTRAL, DEEPSEEK, KIMI` added to the prefix list over leaving them off: `src/utils/pricing.json` prices grok-*, codex-mini and kimi-* models, and `grok-4` would otherwise be recorded as story `GROK-4` — user, answers AR-7
- Prefix list kept closed, as one named constant in `ticket-parser.ts` extended by a one-line edit and a release, over a config-driven or runtime-derived list — user, answers AR-7
- Prefix list seeded by hand from the ticket's tokens and the model families `pricing.json` prices over waiting for analytics counts or reading `pricing.json` at runtime: no analytics access here, `pricing.json` is the in-repo enumeration of the product's model ids, and a runtime read would tie a pure parser to a pricing file; whoever adds a family to `pricing.json` adds the entry.
- O-series (`O1`, `O3`, `O4`) left off the prefix list over adding them: `O1-12` is a plausible real key shape and the requester asked only for the obvious families; `o1-mini-2024-09-12` stays accepted residual.
- Prefix rule applied to prompt scanning only (mention tier and `ticket_mentions`) over applying it to branch names: the branch tier has no reported defect, and the `story:` marker cannot recover a branch story on non-prompt events.
- Drop every candidate in a prompt run whose first segment is on the prefix list over dropping only the candidate whose key is listed: the tails of full model ids (`mini-2024`, `flash-001`) otherwise survive the rejected family and become the story — user, answers AR-6
- Accept the loss of a real key glued by a dash to a leading listed segment (`gpt-4o-EPMCDME-15301`) over a narrower rule that would keep it: a key separated by space or another delimiter is still detected — user, answers AR-6
- Keep the branch tier unchanged by the leading-token condition over extending it to branch runs: `feature/GPT-4-support` still yields `GPT-4` — user, answers AR-6
- A `.` between two digits joins the prompt run over ending the run at every `.`: `gemini-2.0-flash-001` would otherwise split into `gemini-2` and `0-flash-001` (first segment `0`, not listed) and keep `FLASH-001`; the UUID rule's run is unchanged unless the plan shows no outcome differs — user
- Both rules read runs from one tokenizer over two separate run definitions: the next join change is one edit, and the two rules cannot disagree on the same text.
- Keep the key condition (a) anywhere in a run next to the first-segment condition (b) over first-segment only: `my-sha-256` and `x-gpt-4` stay dropped as before, at the cost of leaving `openai-gpt-4o-mini-2024-07-18` as residual.
- Source and ranking choices as an options object `{ source, preferUpperCase }`, defaults prompt and false, over positional parameters or separate functions: callers and tests that pass `(text, limit)` keep the stricter prompt behaviour and first-seen order, and a later option adds no positional argument.
- `TICKET_RE` kept exported and unchanged over dropping the export: nothing imports it, but the doc row names it and removing it is not part of this fix.
- Marker tier left as is over applying the same filter: an explicit `story:` phrase is deliberate.
- Extend existing test files and the architecture doc in place over adding new files, per the run constraints.

## Open risks

- The prefix list is a closed literal; its owner is by convention whoever adds a family to `pricing.json`, nobody monitors prompts; incidence of other tokens (including the O-series, left off on purpose) in real prompts is unmeasured, and wrong ids outside the list keep appearing until it is extended.
- Past wrong `story_id` rows in analytics are not repaired, and older installed hooks keep emitting the old behaviour until upgraded.
