# Spec: CLI explicit-connect, funding route and session-transition handling (EPMCDME-16849, CLI child)

Baseline `origin/main` 916710fb. Size XL (27/36), one slice (no re-split). Story `story.md`. Authority: backend code (bb83b827c + snapshot fix), backend `spec.md` rev 3, then `evidence/backend-contract-handoff.md`. Facts about today's CLI come from `technical-analysis.md` and the spike `cli-session-transition-research.md`.

## Behaviour

1. **Wire (producer side).** On evidence-mode POSTs (`evidence-send.ts:28-44` via `buildAttributionHeaders`, analytics destination) the CLI sends `X-CodeMie-Publication-Contract: <CONTRACT>`, `X-CodeMie-Funding-Route`, and `X-CodeMie-Work-Consent: explicit-folder` only with a non-blank `X-CodeMie-Project`, each once, only when the backend advertises `publication_contracts` containing the negotiated value (`policy-cache.ts`). `CONTRACT` is one constant (value `"1"`) used by the sender, the capability check and echo verification. Absent list, unavailable policy or non-2xx = not supported; never inferred from a 2xx. Existing evidence headers, class derivation and `policy_version` handling are unchanged. Values come only from the frozen record plus the current consent re-check (item 4).
2. **Capability not advertised: bounded refresh, then hold.** A cached policy lacking the list (e.g. fetched before a backend upgrade) triggers one bounded capability refresh through the existing retry/backoff, not 24h silence and not a loop. An expired policy is never used as authoritative for organization/classification and never bypasses the pause/capability contract; the expired list only informs the hold decision, so a network blip does not report "unsupported". Before its first send, a newly stamped session durably chooses its wire mode. Without contract support, only a no-consent session with proven routing and determinate codemie/corporate classification may use the supported old evidence protocol or confirmed legacy protocol. Personal, unknown, consented or unavailable-capability cases hold. The chosen mode never upgrades or downgrades mid-session; earlier funding records without the negotiation marker remain contract-only. A legacy fallback cannot publish funding buckets until a new contract-mode session. Still unsupported for the required mode: hold within the spool retention window (~24h), then suspend with notice; never reported published. Hold statuses (`503 publication_contract_unavailable | personal_storage_unsupported | project_unavailable | project_analytics_not_enabled | destination_unsupported`) behave the same: a cause-specific notice at the FIRST hold, a single bounded clock from the first hold (kept across reason changes and restarts), and at expiry the range is dropped and the session stops with `hold_expired` and a notice (forwarder -> delivery retention -> stop marker, same as the tick path). The forwarder's synthetic hold after an unsupported-contract refresh (`422 publication_contract_unsupported` with no refreshed advertisement) is classified as that hold, never as an ordinary `http_422` rejection; ordinary 400/413/422 rejections keep their semantics. Ordinary retry statuses and accepted history are unaffected. `destination_unsupported` is the backend's refusal of a resolved project destination whose name cannot be a canonical header; the project header stays raw (no encoding). `connect-folder` rejects such a name before saving consent, and the sender stops a consented session whose frozen project is not sendable (`consent_project_unsupported`) instead of omitting project and consent. Retry statuses (`503 personal_destination_unavailable | default_project_unavailable`, unknown 503 reasons, storage errors) use existing spool retry. 422 finals (`publication_contract_unsupported` after one refresh, `publication_contract_requires_session`, `_missing`, `consent_invalid`, `consent_without_project`, `consent_personal_project`) drop the session's data and surface the reason. 200 discards (`session_*_conflict`, `session_project_unavailable`, bound `cli_analytics_disabled`) are terminal unsuccessful outcomes per item 3, not accepted publication.
3. **Response verification.** Parse a recognized backend final-discard body before checking acceptance echoes: it is a terminal unsuccessful outcome, never publication success, with its reason/loss disposition reported. The backend intentionally omits acceptance echoes on discards. An otherwise accepted response is success only if it carries the contract echo and `X-CodeMie-Destination`; for N1 the destination must be `project` and `X-CodeMie-Bound-Project` must equal the frozen project case-insensitively. Missing/mismatched echoes on an acceptance are `response_unverified`: never acknowledged, sending stops (item 8), user notified. No redirects followed.
4. **Work consent** is separate from the contract (contract and funding go on every new-contract request; consent only when granted). User-local, explicit, revocable: a versioned store under `getCodemiePath()` (never in a repo, profile or workspace config), one entry per `hash(canonical folder | backend identity | project)` (`project-allowlist.ts` canonicalisation, `evidence/api-identity.ts`); an unreadable or unknown-version store means no consent. Written only by an explicit connect action, removed by a disconnect action, both on the existing `claude-code-otlp` folder management surface (`connectors/claude-code-otlp.ts:529-728`); no new top-level command.
   - Connect rejects drive/filesystem roots, the home directory and any ancestor of it. Confirmation names the canonical selected folder and project and states that every descendant folder resolving to that project is covered and that conversation content becomes visible to project admins. Ordinary repo subfolders stay usable. No consent is inferred from a broad global profile or a clone. Whether connect also adds an allowlist entry is a plan detail; the global gates are unchanged either way.
   - Applies to a hook iff global gates pass first (collection enabled, not excluded, inside allowlist when one exists), an entry's folder is the hook folder or an ancestor, backend identity and resolved session project equal the entry's, and the project is non-blank. Provenance alone (`project_source` `linked_folder`/`profile`/`none`, cloned config, profile names) grants nothing; a profile-sourced project does count when a matching explicit entry exists (D5). Folder/backend/project/entry are re-evaluated independently from the frozen evidence on every hook and on every forwarder send: a disconnect stops consent-bearing sends from new hooks and from the backlog. It never rewrites a bound session. Entries are keyed by backend and owner, so accounts/backends stay isolated.
5. **No consent is not an error.** The CLI sends contract and funding without consent. The backend keeps N0 derived codemie/corporate on today's work route and puts derived private personal/unknown in owner-only personal storage (or holds for unsupported users). The CLI never selects a destination or switches the profile.
6. **Funding route** is computed once at the first stamp beside `classify()` from the same routing evidence, frozen in the record (first-wins; never recomputed, compared or used as access). `api_based` only when positively established (`routedViaCodemie` together with `Routed-Via-CodeMie=true`, or a first-party API key positively in use on the first-party endpoint). Cloud-provider flags (Bedrock/Vertex/Foundry) do not prove a usable API credential, so cloud providers are `unknown` in this scope; positive cloud support is not implemented. `subscription` only when `oauthAccountPays()` (`evidence/routing.ts`) is true with no contradicting source. Everything else, incl. unproven routes, apiKeyHelper, gateway auth outside the CodeMie route, Anthropic profile/federation, unreadable settings, contradictions, is `unknown`. First-wins funding applies to both N0 and N1; exact-project confirmation applies to N1 only. N0 keeps today's fallback (never a guessed-project mismatch). No credentials logged or sent.
7. **Collection disable and exclusions** gate first and unchanged: nothing published, no consent evaluation, no session/activity/content record written by hooks while disabled or excluded.
8. **Publication stop (fail-closed owner).** One mechanism reused by every suspension, hold-expiry and `response_unverified`:
   - A required stop is never only logged: a marker that cannot be written leaves the stop intent in the session status (the spool's durable state) and blocks every later send, tick and restarted daemon until the marker is written; where data is still held (retention expiry, the tick's hold expiry) the backlog and hold are kept and the stop is retried before anything is dropped. If neither the marker nor the status can be written the intent exists in this process only and is reported as such.
   - A tiny atomic stop marker, a sidecar file in the existing evidence namespace keyed by `recordKey(backend, owner, session)`, outside the create-once evidence record. Written atomically by the hook or daemon, never deleted by reconnect; holds a bounded reason code and notice state. Retain it while a corresponding evidence record or queued data can still authorize publication. Cleanup requires both to be absent plus the retention margin; a later resume then lacks required scope evidence and fails closed. No per-session state is written for unknown sessions while disabled or excluded.
   - A single `isStopped(key)` reader runs in the hook before spooling and in the daemon tick and forwarder before any network send, ack or backlog drain.
   - A non-startup hook (`SessionStart.source` resume/fork, or any later hook) whose session has no record or marker is a session of unknown scope: it writes a marker and nothing is published. Missing, corrupt or lost required scope evidence fails closed. Record eviction or reconnect cannot resurrect publication; only a new session id (startup or `/clear`) starts fresh.
   - At a privacy stop, all further sends for that session stop, including backlog; no partial-drain ordering or `through` boundary is introduced. Already accepted history stays unchanged. Unsent ranges are retained under existing bounded retention and reported as unpublished on expiry, never falsely acknowledged or backfilled after reconnect. New-session guidance is shown. Already in-flight requests cannot be recalled; the check precedes each new network send.
   - Notice-pending lives in the same marker. The hook reads it on its next run and surfaces it once, including daemon-side hold/echo failures; the daemon's `logger.warn` is a diagnostic only, not a user-visible promise.
9. **Transitions.** Reuse the session pin, record and `onUntrackedHook`; no ledger.
   - `/clear`: new session id, fresh record, fresh consent/funding for its cwd.
   - resume/fork: per item 8; only a session with a record continues, and only while its frozen scope still holds: the frozen collection generation, the frozen project (canonical form) and, for a consented session, the originally granted consent still covering the folder. Consent is frozen at session start: connecting a folder applies to NEW sessions, so an existing unconsented session stays unconsented on resume (no auto-upgrade, no wider history visibility, no inferred consent); a consent that was granted and is later revoked stops the session. A record without a frozen collection generation (made before generations were recorded) cannot prove this continuity for ANY wire protocol or funding claim: it is suspended with a one-shot notice and needs a new session; nothing is invented, upgraded or moved. The same rule runs in the live hook, the owner-pending replay, the tick and the forwarder (including legacy-mode sends); a record with a frozen generation is judged on its scope even without a funding claim. Fork replay is suspended, not sent.
   - In-session folder change: hook cwd resolving to another project, unconnected or excluded scope stops the session (marker), including via `onUntrackedHook` for an already-recorded session silenced by exclusion.
   - Collection disable/re-enable: the explicit settings action increments and stores a `collection_generation` in the existing claude-analytics preferences (`claude-code-otlp.preferences.ts`, atomic update). This is configuration metadata at the user's action, not session recording while disabled. The generation is frozen in the record at the first stamp and compared on every enabled-session hook and forwarder send; a mismatch stops the session (marker) and requires a new session id. A failed preferences write fails closed; arbitrary external edits to the file are not assumed to preserve continuity. Existing sessions whose continuity cannot be established after re-enable are suspended.
   - Suspended: no sends, no backfill, hooks return normally (Claude never blocked), one actionable notice, sticky until a new session id. No mid-session personal toggle.
   - Duplicate consumption: an `/clear` pair and a resume in the same scope send each usage entry once. Funding first-wins applies to every new-contract session (N0 and N1); exact requested-project confirmation applies only to N1.
10. **Notification.** One-shot per suspension/first hold via the hook output channel (item 8 bullet 5). Hook stdout is currently silent (`tests/integration/hook-stdout.test.ts`); a real functional check that the user sees it and the model context does not is an acceptance item, with `logger.warn` as fallback.
11. **Header hygiene.** Header-injection `onRequest` merges `destination: 'model'` headers (`header-injection.plugin.ts:145`), which never carry publication, consent or funding headers, so that merge alone is not an analytics bypass. The analytics consumer is the forwarder (`forwarder.ts:59-64`, `evidence-send.ts`): it builds headers from credentials plus the frozen record and does not forward inbound client headers. Work: (a) on the proxy `onRequest` path, strip the publication-contract, funding-route, work-consent headers (and other analytics-only names) from model requests case-insensitively, keeping unrelated headers; (b) analytics-send takes consent, funding and contract only from the frozen record and current store, never from spooled or inbound headers, with a test over the cloned-settings/OTLP ingress (`otlp.plugin.ts` handleRequest) that an injected header in any case never reaches the backend request. No new proxy framework.
12. **Unchanged:** legacy-header behaviour for old CLIs, existing allowlist semantics, class derivation, pricing, Control Plane/UI. Release order: production CLI activation follows a compatible backend deployment; local dev and E2E use the reviewed backend worktree.

## Acceptance criteria

- AC1: connected folder, backend advertising the contract -> real CLI sends contract, consent, funding; real backend binds the canonical project; the reader returns the session for a super/project admin.
- AC2/AC3: no connection, profile-sourced project without a matching entry, or global profile in an unrelated folder -> no consent header; private personal/unknown lands owner-only (or hold) and nothing in a work project; derived codemie/corporate keeps today's work route.
- AC-consent: a cloned `.codemie` config, other backend/project/account, moved folder, a disconnect (incl. queued backlog) each give no consent; connect on a root, home or ancestor is refused; the confirmation names the canonical folder and descendant coverage; the store is outside every repository.
- AC4: collection disabled or folder excluded -> nothing published, no session/activity record written.
- AC5: funding table (item 6) holds, incl. cloud providers and contradictions -> `unknown`, first-wins across a mid-session model/auth change, no credentials in logs or headers.
- AC8: /clear, resume (same/other folder, session first seen excluded), folder change, fork, repeated startup/resume, and a disabled then re-enabled existing session -> per items 8-9: no private backfill, no duplicate consumption, no upload after stop/record eviction/reconnect, already accepted history unchanged, unsent backlog retained only under bounded retention, suspension with notice, Claude usable. **Explicit gap:** interactive TUI `/clear` after `cd` (research U1) stays an unresolved manual case with its manual steps; not claimed passed.
- AC9/AC11: old backend (no list) -> bounded refresh, safe pre-send negotiation only as in item 2; unsafe sessions hold/suspend; frozen protocol survives restarts and backend upgrade/rollback; 422 `publication_contract_requires_session`, final discards with and without echo, and echo mismatch behave per items 2-3 against the real backend; legacy and L1 boundaries unchanged.
- AC-hdr: injected consent/funding/contract headers in any case, via model path and via cloned-settings OTLP ingress, never alter the analytics request.
- AC-notify: the first-hold/suspension notice (incl. a daemon-originated one) is observed functionally.
- AC-E2E (shared, owned here): real CLI producer -> real backend ingest -> Postgres -> analytics reader across hook -> durable state -> queued forwarder -> backend/reader, for consented personal work, private/unknown without consent, disable/exclusion, transitions, old-backend/legacy boundaries, no duplicated consumption, using task-owned loopback Postgres containers only; `pg-epmcdme16833` is never touched. Wrapper launches stay on `--profile claude-personal`. Synthetic events and mocked transports do not count; any synthetic check is labelled.

## Non-goals

- Backend, Control Plane, UI, ticket attribution, Cost per Point, pet-project detection.
- Incidental changes to global profiles, CLI defaults, other hooks or the installed 0.16.4 wrapper; automatic profile switching; a personal/private toggle; a profile-name rule.
- A new tracking, ledger, proxy or provider framework; recording sessions or content in disabled/excluded folders.
- Sending credentials; treating funding as access or billing proof; repository-carried consent.
- Latency benchmarks or held-bytes matrices absent a concrete risk.
- Publication, MR creation or merge.

## Decisions

- New-contract participation is separate from work consent over folding consent into the contract header.
- Consent store is user-local keyed by canonical folder + backend + project over repo/profile/workspace config or `project_source`.
- Connect/disconnect live on the existing `claude-code-otlp` folder management surface over a new top-level command.
- Connect refuses roots, home and its ancestors over allowing any folder.
- A profile-sourced project counts only with a matching explicit entry over provenance alone or never.
- Unadvertised capability: bounded refresh, then only safe no-consent codemie/corporate sessions can freeze an old protocol before sending; all other new sessions hold. Previously contract-bound sessions never downgrade.
- Expired policy informs the hold decision only over being authoritative for classification.
- One negotiated contract constant over literals per module.
- Funding frozen at first stamp, first-wins, over recomputing per request.
- Publication stop is a sticky sidecar marker outside the evidence record, checked by hook, tick and forwarder, over a flag inside the evictable record.
- Unknown scope on a non-new session fails closed over continuing from the pin.
- Privacy stop blocks the whole session backlog; retain unsent ranges under existing expiry rather than implement a partial-drain boundary or acknowledge unsent data.
- Notice-pending reuses the marker with a hook-side reader over relying on daemon logging.
- Disable/re-enable boundary is a `collection_generation` bumped at the explicit settings action in existing preferences over accepting the gap or passive recording while disabled.
- Header sanitizing: strip analytics-only headers from model requests and derive analytics values from the frozen record only over claiming a proxy bypass.
- Notification via the hook output channel, functionally verified, over a new status surface.
- Interactive TUI `/clear`-after-`cd` stays a manual gap over a third automation attempt.

## Open risks and assumptions

- Old-protocol fallback preserves ordinary derived work analytics but cannot add funding buckets; full subscription/privacy functionality still needs the matching backend. Personal/unknown/consented sessions and pre-negotiation contract records remain held without it.
- Full backend guard/baseline limits and held-session re-upload per retry are backend-side and not CLI blockers.
- Notification reach and exclusion from model context are unverified until functionally tested.
- Continuity across arbitrary external edits of preferences or evidence files is not guaranteed; unknown continuity suspends.
- Marker/consent-store schemas are plan-level; concurrent-hook behaviour in real Claude is unmeasured. Marker cleanup cannot reauthorize an existing record or queue.
- U5/U6 auth variants stay `unknown`; funding `unknown` share for `/login` starts is accepted and measured after rollout.
