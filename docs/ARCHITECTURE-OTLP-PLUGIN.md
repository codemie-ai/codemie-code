# OTLP Hook-Event Plugin Pattern (`OtlpAgentAdapter`)

**Scope**: any plugin extending the abstract `OtlpAgentAdapter` (`src/agents/core/OtlpAgentAdapter.ts`), under `src/agents/plugins/<name>/`. Today that's `claude-code-otlp` only.
**Status**: Living doc — update when the dispatch pattern changes or a second adapter lands.

## 1. What this pattern is

An `OtlpAgentAdapter` is not a chat agent. It's the ingestion point for one coding tool's native hook/event surface, turned into CodeMie's analytics pipeline (session summaries, usage, auth gating). `OtlpAgentAdapter<TInput, TBlockOutput>` is an abstract base class: it owns the fixed `processOtlpEvent` flow and resolves agent-independent common fields at hook time; each adapter supplies only the tool-specific parts.

```ts
export abstract class OtlpAgentAdapter<TInput, TBlockOutput = Record<string, unknown>> {
  abstract readonly name: string;
  readonly type = AgentAdapterType.OTLP;
  async processOtlpEvent(raw: string, deps: OtlpAdapterDeps): Promise<void>; // fixed flow

  protected abstract parseHookInput(raw: string): TInput | null;   // null => ignore
  protected abstract extractHookContext(input: TInput): OtlpHookContext;    // { cwd, prompt?, sessionId? }
  protected abstract isTracked(input: TInput): Promise<boolean>;   // allowlist gate
  protected abstract evaluate(input: TInput): Promise<ForwardDecision<TBlockOutput>>;
  protected abstract resolveAgentFields(): Promise<Record<string, unknown>>;
  protected abstract resolveEventType(event: Record<string, unknown>): string;  // `type` of a native event
  protected abstract buildEventId(event, payload, timestamp): string;  // deterministic `<kind>:<session>:<discriminator>`
}

export interface OtlpAdapterDeps {
  ensureOtlpProxy: (agentName: string) => Promise<void>;
  // Sends one hook invocation's events as a single batch; true only for a 2xx response.
  forwardOtlpEventsToSpool: (events: Record<string, unknown>[], agentName: string) => Promise<boolean>;
}

export interface OtlpHookSpoolData {
  agentName: string;
  hookEvent: string; // the complete event (serialized), built at hook time
}
```

Spool forwarding is injected through `OtlpAdapterDeps` (supplied by `hook.ts`) rather than imported, so `core/` has no upward imports and the base class is testable with plain fakes.

Adapters can override `requiresSpoolAcceptance(input)` for enforcement events. If the local batch is rejected after any configured retry, the base class raises an `AnalyticsSourceError` through `onHookError`, after finalizing with `accepted: false`. Copilot Chat opts in for session start, prompt submission and tool permission checks; Copilot CLI opts in for prompt transformation and tool permission checks. Their existing error handlers emit the host-specific block, prompt replacement or tool denial. The default is `false`, preserving Claude's cursor/retry behavior. This checks local durable acceptance, not backend delivery: a backend outage does not block work once the local spool accepts the batch.

Everything downstream of `processOtlpEvent` — spool, forwarder, analytics API — is already agent-agnostic and shared. Nothing in it is specific to any one tool's hook names or payload shape; that lives entirely inside each adapter.

## 2. Pipeline

```
<tool>'s native hook/event fires (agent-specific names/payload)
        │ JSON on stdin
        ▼
codemie hook --agent <adapter-name>        (src/cli/commands/hook.ts)
        │ looks up adapter via AgentRegistry.getAnalyticsAgent(name)
        ▼
OtlpAgentAdapter.processOtlpEvent(rawEvent, deps)   (base class, fixed flow)
        │ parseHookInput → isTracked → ensureOtlpProxy
        ▼
evaluate(input) → ForwardDecision          (§3: shape every adapter follows)
        │
   ┌────┴─────┐
 block       forward
   │           │
 log +     every record built: type, secret masking, truncation, common +
 suppress  agent + context fields, schema_version, event_id
 (adapter-     │ one batch POST for the whole invocation
  specific)    ▼
         proxy daemon spool (one line per event, OtlpHookSpoolData { agentName, hookEvent }) - stores as is
                                                        │
                                                        ▼
                                  otlp-spool/forwarder.ts (background, transport only)
                                                        │
                                                        ▼
                                              CodeMie analytics API
```

- `forwardOtlpEventsToSpool` (`src/agents/plugins/utils.ts`) is shared: POSTs `{ agentName, hookEvents }` (every record from this one invocation) to the local proxy daemon's `/v1/analytics/hooks` in a single request (3s abort), and returns a boolean — `true` only for a 2xx response — instead of swallowing the outcome. Never throws. A dead daemon or a non-2xx response makes it return `false`; a handler with a cursor (§3.4) only commits that cursor when it sees `true`, so a failed send never advances past events that never left the hook process.
- **The daemon appends the whole batch as one spool write** (`otlp.plugin.ts`'s `handleHooks`): one hook invocation is single-session, so events without a `session_id` are discarded individually and a batch mixing more than one non-empty `session_id` is rejected whole (400). It answers **500** when the spool write itself fails, and 202 only once the batch is durable — the honest half of the all-or-nothing contract `forwardOtlpEventsToSpool` depends on.
- **The forwarder is transport only** (`otlp-spool/forwarder.ts`). It unwraps the spool envelope (still one line per event, `OtlpHookSpoolData`), POSTs `hookEvent` byte for byte, advances the cursor, and retries on 401/403 or 302 login redirects. Redirect following is disabled so an SSO login page returned with 302 cannot be mistaken for successful telemetry delivery. Repeated 401/403 or 302 responses mark credentials stale and leave spool cursors untouched; other redirect statuses are treated as ordinary unsuccessful responses. It does no context resolution and no event enrichment, and never calls into any adapter. It owns only `baseUrl` (from daemon state) and the credentials. The one thing it reads from an event is `type === 'agent.session.end'`, to call `markSessionEnded`. Besides the auth headers it sets `X-CodeMie-Project` on all four POSTs (event-hooks, logs, metrics, traces) to the session's bound project (see "Project gate" below); the daemon's own current project is never used.
- **Project gate** (`otlp-spool/session-project.ts`, `session-status.ts`, `spool-io.ts`, `tick-processor.ts`, `forwarder.ts`). The backend discards analytics whose project context is missing or ambiguous (it answers 200 and drops irreversibly, see `.ai-run/guides/integration/cli-analytics-events.md`, "Project gate"), so the CLI never knowingly sends an ambiguous session and does not rely on the backend as the safety net.
  - **Status fields**: the session status file holds `project` (set-once, first usable `codemie_project_name`, original spelling), `projectConflict` (distinct names seen, set-once and sticky), `projectSeal` (see "Hooks seal") and `projectScanned`. They survive profile change, daemon restart and cursor advancement, and end only when the sweeper deletes the drained, idle session; a session that wakes after that is a new session. Names are compared case-insensitively and are read from the hook event's top level (events no longer carry `raw`; older spooled events may still carry it, and `session-project.ts` keeps reading it from them). A blank name is ignored; a non-blank name that cannot be a header value (leading/trailing whitespace, control or non-Latin1 characters) is a conflict on its own.
  - **Atomic ingest**: `appendSpool(sessionId, 'hooks', data, projectNames)` appends the hooks, observes the names and decides bind or conflict in one critical section under the session lock, writing the status before the bytes (a failed append leaves a conservative status and the hook client retries the same batch). The whole batch plus the stored binding is judged together, so a mixed first batch conflicts. Hook bytes are still spooled on conflict and are never filtered when they are written; the endpoint still answers 202. When a bound session turns into a conflict, the seal is recorded in that same status write (see "Hooks seal").
  - **Legacy recovery**: a status without `projectScanned` whose hooks file exists has its on-disk hooks (acknowledged prefix included) scanned once, under the lock: exactly one distinct name binds, none stays unbound, two or more conflict.
  - **Nothing is sent for a conflicted or unbound session** on any of the four streams, except the sealed hooks prefix described under "Hooks seal". Its unsent backlog is discarded locally (cursors to EOF, debug log with the session id only) rather than held: a held backlog never drains, so the session would never be swept and would be re-evaluated every tick forever, while the backend would discard the data anyway. The tick and the snapshot functions apply one shared policy under the lock (`evaluateProjectPolicy`, executed by `applyProjectPolicyLocked`), so they cannot disagree: the **tick** (before the completeness gate; the primary point, because with `OTLP_ALLOW_HOOKS_ONLY_FORWARD=false` a hooks-only session never reaches `forwardSession` and its snapshots) and the **snapshot functions** (close the window after the tick). An OTEL-only session (no hooks file) is left to the existing wait/skip path so late hooks can still bind. Trade-off: a session whose hooks so far are all blank is discarded at the first tick, so OTLP bytes discarded before a named hook binds it are lost.
  - **Hooks seal** (`projectSeal: { v: 1, project, hooksEnd }`): when a session that was bound to project A turns into a conflict, the status write that records the conflict also records `hooksEnd`, the exact size of the hooks file before the conflicting append. Only the hooks below it are provably A's, and only records whose own `codemie_project_name` (top level; `raw` only on older spooled events) is non-blank and equals A are sent, under header A; blank-named, other-project and unparsable records are consumed unsent. Everything else is discarded as before: all OTLP logs/metrics/traces of the session (they carry no project and arrival order is not proof of ownership, so an OTLP chunk that arrived before the conflicting hook, or after it, is never attributed), the conflicting hook and every later hook, even one naming A again. The sealed prefix is flushed by the tick hooks-only and at once (no wait for OTLP that will never be sent); when it is acknowledged the rest of the hooks is discarded. A session that was never bound (a mixed first batch, blank names) or was found conflicted by the legacy scan has no seal and is discarded as before. The seal is written once, before the bytes land, with a size that cannot exceed the file; the effective end is also clamped to the file size, so nothing waits for bytes that are not there, and a partial record at the end of the prefix is consumed instead of awaited. It is read back only if it is exactly what the writer produces (version 1, sendable project, safe non-negative end, a conflict that names the project); anything else, including every status written before this field existed, means the old behaviour, and data already discarded is not recovered. A recreated hooks file drops the seal (it pointed into the old file) and keeps the conflict. With `OTLP_ALLOW_HOOKS_ONLY_FORWARD=false` the sealed prefix is discarded too: it can only travel without OTLP, and the operator opted out of that. Two `warn` lines per session at most: one when the conflict is recorded, one (per daemon run) when unsent data is discarded, naming the counts and the reason, never prompt content.
  - **Disk limitation**: advancing a cursor frees no space. The sweeper removes the spool files only after every stream is drained and the session has been idle for the grace period (`OTLP_ENDED_SESSION_GRACE_MINUTES` 15 after `SessionEnd`, `OTLP_ABANDONED_SESSION_GRACE_MINUTES` 60 otherwise, measured from the last spool-file write), so a blocked session that keeps producing keeps growing its files until it goes quiet and is swept. No truncation or cleanup is done by this change.
  - **Guarantee and limits**: data not yet sent when the conflict is persisted is never sent, except the sealed hooks prefix; no new OTLP attempt is permitted once the conflict is persisted, subject to the check-to-wire window below. OTLP sent earlier, and a request already built or on the wire when the conflict was persisted, are not undone. So a session that changes project loses the OTLP-derived metrics it had not yet delivered (the accepted limitation of the project binding, not a bug) and the cost of its other-project work is not reported. A request already built and in flight, and sends completed earlier, are not undone; OTLP bytes exported before the first conflicting hook was ingested cannot be told apart; `send()` re-checks `isSendAllowed` before every attempt (including the 401/403 retry), per stream and per snapshotted byte range: a sealed session passes it for its hooks prefix only, never for an OTLP stream, and a range that is no longer the next one is refused. A hooks snapshot built while the session was bound is not filtered (blank-named records included), so once a conflict seals the session that snapshot, and an auth retry built from it, is refused too: nothing is posted and the cursor is not advanced, and the next tick re-snapshots the prefix through the only-this-project filter, so the provable prefix is not lost. This narrows the window between snapshot and wire without closing it.
  - **Backend answers**: any 2xx completes the batch (a 200 discard is final: cursor advances, credentials not marked stale); 503 (policy lookup failure) and other non-2xx are retried; 401/403 behave as before.
  - **Lock rules**: the session lock is a non-reentrant promise chain without timeout. Code running inside it may use only `readStatus`/`writeStatus`, `stat`/`readFile`/`appendFile` and pure helpers (`resolveLegacyProjectLocked`, `discardBacklogLocked`, `applyProjectPolicyLocked`, `session-project.ts`); it must never call `updateStatus`, `ensureStatus`, `advanceCursor`, `appendSpool` or a `snapshot*` function, or the chain waits on itself and wedges the session. The lock is never held across HTTP.
- **Stale-credential recovery is in-process, no restart required.** A persistent 401/403 sets `otlp-spool/auth-state.ts`'s `credentialsStale` flag, which suspends every forward (`forwarder.ts`'s `send()`) while spool data keeps accumulating on disk. `OtlpInterceptor` (`otlp.plugin.ts`) re-reads the credential store through `resolveFreshCredentials` in `otlp-spool/auth-state.ts` (same lookup as `CodeMieProxy.start()`: `syncCodeMieUrl` credentials first, else the main platform credentials) when that flag is set — on its own forwarding tick, and opportunistically when inbound hook/OTLP traffic arrives after a successful SSO re-login. A successful read replaces the in-memory credentials and clears the flag; forwarding resumes on that tick or the next tick after an inbound refresh. Failed or empty reads leave the flag set, so delivery retries automatically and no spool data is discarded.
- **The event is built by the base class at hook time** (`buildEvent`), because the forwarder runs in a long-lived daemon whose env (cwd, active profile, credentials, CLI version) is frozen at spawn. Per record, in order: `type` (an explicit `type` on the record wins, otherwise the adapter's `resolveEventType`), removal of the fields the adapter lists in `droppedFields(hookEvent)` (default none; Claude Code drops `last_assistant_message`, `session_crons`, `background_tasks`, and `custom_instructions` on every event, plus `message` and `title` on a Notification, and keeps the `title` of the session summary), normalization of Claude hook `effort: { level }` to the scalar level (malformed effort objects are omitted), **pattern-based secret masking of every field for all adapters, always on** (best effort: every field is scanned, but only the formats listed here are recognised, so an unlabelled or unfamiliar secret passes through; `maskSecretsDeep` in `src/utils/security.ts`: embedded API keys and tokens (OpenAI, Anthropic, AWS, GitHub, GitLab, Slack, Stripe, Google, npm, Hugging Face), JWTs, space-separated secret flags (`--password x`, `curl -u user:pass`, `mysql -pSECRET`), `Bearer` and `Authorization` values, PEM blocks, `scheme://user:pass@host` credentials and `NAME=value` / `"name": "value"` pairs whose name ends in a secret word are replaced by `[REDACTED]`, and a string under a sensitive key is redacted whole; identifier fields such as `session_id`, `type`, `timestamp`, `file_path`, `tool_name`, `tool_use_id`, `agent_id` and `fork_agent_id` are skipped, and no generic entropy pattern is used, so `"agentId"` in a `tool_response` survives), then truncation of the masked values (mask first, then cut: `prompt` to 200 chars, `tool_input` / `tool_response` / `error` / `description` to 300, so a secret straddling a cut is never half-shown; an incoming `raw` is dropped — a Skill `agent.tool.end` also carries `fork_agent_id`, the fork's id the Claude Code adapter reads from the uncut result, cut to the same 300). The Claude Code adapter also strips file content from `agent.tool.start`, `agent.tool.end` and `agent.tool.error` for a `Read`, `Edit`, `MultiEdit`, `Write` or `NotebookEdit` of a credentials file: `tool_input` shrinks to the path and `tool_response` (and a failure's `error`) is omitted. A file counts as credentials when it is (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `credentials*`, `.npmrc`, `.netrc`, `.pypirc`, `.git-credentials`, anything under `.aws/`, `.ssh/`, `.gnupg/`); `tool_name` and the path are kept. The Copilot CLI adapter masks its own free-text fields before its 300-char cut. Then `prompt_body` (from the masked, cut `prompt`), `session_id` coerced to a string, `cwd` (always the hook's cwd, also for transcript-derived events; stamped as the repository identifier `extractRepository(cwd)` -- `parent/current`, `Cowork` or `unknown` -- never the absolute path, which does not leave the hook process; `repo_remote` is unchanged), `schema_version: 2`, a deterministic `event_id`, and `timestamp`. No adapter emits a `raw` field any more (it used to mirror the full enriched event): every enriched field lives at the top level, including the daemon-built Copilot CLI usage events; spool lines written before this change may still carry `raw`. The same reduction applies to the subagent events' `worktree` field (`agent.subagent.usage` / `agent.subagent.stop`): it is `extractRepository(cwd)`, `''` when the hook carries no `cwd`, never the absolute path. `event_id` is deterministic, `<type>:<session_id>:<discriminator>`, produced by the adapter's `buildEventId` (`claude-code-otlp.event-id.ts`). It is the backend's dedup key (the first record with an id wins), so templates use an immutable natural key only where newer values cannot appear for it — `agent.git.snapshot` uses `git_head_end`, `agent.session.summary` phase + `ended_at`, `agent.session.compact.done` the boundary timestamp. A record that can be re-sent with newer values is content-hashed: `agent.usage.request` and `agent.subagent.usage` include their payload, so a later pass with more tokens/usage gets a new id that the backend stores and `max()`/latest-merges. `agent.session.env` and every native hook event are content-hashed from their payload plus the resolved timestamp — an exact resend keeps its id, while a newer env snapshot becomes a new row (harmless: the backend keeps the latest value by timestamp, and an A → B → A switch is no longer dropped as a duplicate of A).
- **Timestamp**: the event's own valid timestamp (e.g. the transcript line time on `agent.usage.request`), else one `new Date()` captured per hook invocation. It is persisted inside the spool line, so every retry re-sends the same bytes.
- **Field resolvers live in `src/agents/core/event-fields/`** (`repo-fields.ts`, `identity-fields.ts`, `env-fields.ts`), one async function per field family, each returning a flat record and `''` per field on failure (never throws). Import the files directly, not through a barrel: `codemie hook` is a fresh process per event, so a barrel would load resolvers the event does not need. The base class composes the *common* ones (below) into every event; an adapter composes *opt-in* ones (`resolveEnvFields`, `resolveIdentityCandidateFields`, `resolveGitHeadFields`, `resolveGitCommitFields`, and the sync `parsePromptFields` from `core/ticket-parser.ts` for `agent.prompt.submit`) only into the events that want them, in that event's handler, with the hook payload spread first so it cannot override a resolved value. `resolveGitHeadFields(ctx, 'end')`/`resolveGitCommitFields` back `agent.git.snapshot` (`SessionEnd`, see §6). This shared directory stays agent-agnostic (no tool's own payload shape leaks into it); an adapter that needs resolvers tied to *its own* tool's hook/payload shapes keeps those in its own plugin directory instead — see `claude-code-otlp/event-fields/` in §6 for the Claude-specific example — never in this shared one. A `build*Event()` for a non-transcript-derived synthetic event (`agent.session.env`, `agent.git.snapshot`) is *not* a field resolver and does not live here either — see the note on `claude-code-otlp.plugin.ts` in §6.
- **Common fields resolved by the base class at hook time**: `git_branch` (`detectGitBranch`), `repo_remote` (`detectGitRemoteRepo`), and `story_id` / `story_source` (`core/story-resolver.ts`, priority explicit env/config file -> marker -> branch -> mention; marker and mention only when `extractHookContext` supplies a `prompt`). Merge rule: a record's own non-empty string value wins, otherwise the resolved common value; `''` / `undefined` never clobber. Branch drift correction: a hook fires once per turn, on the branch current *at that time*, but a record can carry its own `git_branch` describing something that happened earlier on a different branch (`agent.usage.request`'s transcript-line branch is the current example — the branch can change mid-turn between the transcript lines it derives events from). When a record's own (post-merge) `git_branch` differs from the hook-time one and the hook-time story is branch-tier or unresolved, `mergeCommonFields` re-derives the story from the record's own branch via `resolveBranchStory()` instead of keeping the hook-time story; an explicit/marker/mention story is never touched, since those tiers aren't branch-scoped. `resolveAgentFields()` overrides everything (platform, version, entrypoint, …).
- **Identity fields resolved by the base class at hook time** (part of the common fields, stamped over the event), once per invocation, each independently (one's failure never blanks another): `user_email` (claims of the SSO credentials), `developer_name` / `identity_source` (`core/identity-resolver.ts`: jwt -> git -> codemie_cli -> os), `codemie_cli_version` (`getCurrentCliVersion()`, i.e. the package running the hook). A failed resolution yields empty strings, never a dropped event.
- **`codemie_project_name` resolution order**: `CODEMIE_PROJECT` (exported into the launched agent's process env by the provider templates, the same source `Session.project` uses) first — it is set once for the whole session and cannot drift as the hook's `cwd` moves, and is never pinned against (see below) since it is already fixed per session. Otherwise, with a `sessionId` (from `extractHookContext`): the per-session pin (`core/session-project-pin.ts`) if one exists; else the nearest `.codemie` found by walking up from `CLAUDE_PROJECT_DIR` (set once at session start, unlike `cwd`) toward the filesystem root (`ConfigLoader.load(configDir, { name: activeProfile })`), or the global active profile — pinned, for that session's later hooks to read back unchanged. Without a `sessionId`, or without `CLAUDE_PROJECT_DIR` (a tool other than Claude Code), resolution falls back to the hook's own `cwd`, unwalked and unpinned, exactly as before this existed.
- **Per-session project pin** (`core/session-project-pin.ts`): plain `claude` sessions (not `codemie-claude`) have no `CODEMIE_PROJECT`, so without the pin their project would still be re-derived from the global active profile on every hook — a mid-session `codemie profile switch` would then look exactly like a second, conflicting project and drop the rest of that session's analytics (the project gate, § above, cannot tell a genuine project switch from its own re-resolution noise). The pin removes that noise by resolving once and reusing the result: the first hook of a session that resolves a non-blank project writes it to `getCodemiePath('otlp-session-project', '<sha256(sessionId)>.json')` with an exclusive (`wx`) create — `sessionId` is hashed so it can never be used as a path, and the exclusive write means a session's hooks that run concurrently all converge on whichever one of them wins the race, read back by every loser (including the writer's own later hooks). Entries expire after 24h (read-time check, best-effort delete), long enough for a `--resume`d session picked back up the next day. This is purely a hook-side cache for one field; it is not the project gate, does not touch the daemon's spool, and does not change which events are sent.
- **This is a different project than the one on model traffic.** `X-CodeMie-Project` on model requests (`header-injection.plugin.ts`, `config.project`) is the proxy daemon's own active profile at the time it was started — one value for the daemon's lifetime, read once, never re-resolved per hook or per session. `codemie_project_name` above, and the project gate's bound project (§ project gate), are resolved per launched-agent-session instead. The two agree in the common case (one daemon, one profile, no mid-session profile switch) but can diverge: a daemon shared by sessions in repos with different projects attributes cost to the daemon's project while analytics split per session, and `codemie profile switch` while sessions run changes nothing already-running sessions see. For cost attribution the proxy's `config.project` is authoritative; `codemie_project_name` is analytics-only and never feeds the model-traffic header.
- **Credentials (SSO only)**: `core/hook-credentials.ts` (`resolveHookCredentials`) reproduces the daemon's choice from daemon state: the credentials stored for `syncCodeMieUrl`, else for `targetUrl` (`SSOProxy`'s `syncCredentials || credentials`). The OTLP daemon is spawned without `--auth-method`, so it always runs as `sso`. JWT is not supported in this flow: a JWT profile gets no credentials in the hook, so identity falls through to git, codemie_cli and os (`identity_source` records the winner). Reading stored credentials clears expired SSO ones, as at daemon start.
- **Effort changes**: on `PostModelSwitch`, an empty effort clears the previous env snapshot value because the newly selected model may not support effort. Other full env refreshes, such as `ConfigChange`, retain the previous value when the hook omits effort.
- **Story granularity**: each hook subprocess resolves independently. A `Stop` after a prompt containing `story: ABC-1` gets the explicit / branch story, not the marker story. Carrying it across a session would need per-session state.
- **Known limitations**: (1) the explicit story tier reads `<cwd>/.claude/analytics.local.json` by default (Claude-flavoured); `resolveStoryFor` takes `explicitConfigPath` so another adapter can override it. (2) The block path prints `JSON.stringify(decision)` to stdout, which is Claude Code's hook protocol; a tool with a different block protocol must make that step overridable (e.g. an `emitBlock()` method).
- **Rollout**: the daemon outlives CLI upgrades. An old daemon recomputes `story_id`, `story_source` and `repo_remote` from its own env and overwrites the hook's values until restarted (`git_branch` is kept). Restart the proxy daemon after upgrading.
- **Known limitations**: (1) the explicit story tier reads `<cwd>/.claude/analytics.local.json` by default (Claude-flavoured); `resolveStoryFor` takes `explicitConfigPath` so another adapter can override it. (2) The block path prints `JSON.stringify(decision)` to stdout, which is Claude Code's hook protocol; a tool with a different block protocol must make that step overridable (e.g. an `emitBlock()` method). (3) `ensureOtlpProxy` (the allowlist/proxy-readiness gate, run before `codemie_project_name` is resolved) still keys off the hook's own `cwd`, unwalked — a tool without `CLAUDE_PROJECT_DIR` support, or a hook whose `cwd` has no `.codemie` anywhere above it, can still gate on the wrong profile even though `codemie_project_name` itself no longer does.
- **Rollout**: the daemon outlives CLI upgrades. Restart the proxy daemon after upgrading. Old-format spool lines and a stale daemon are not handled and produce bad events. For a clean run, stop the daemon and delete `getCodemiePath('proxy', 'otlp-spool')` before the first hook. An old daemon keeps the old behaviour (no `X-CodeMie-Project` header, no project gate) until it is restarted.
- Wiring which native hooks/events call `codemie hook --agent <adapter-name>` is entirely tool-specific — see §6 for the Claude Code connector; a different tool has its own.

## 3. The dispatch pattern every `evaluate()` follows

`ForwardDecision<TBlockOutput>` is a shared generic type exported from `OtlpAgentAdapter.ts`; the adapter binds `TBlockOutput` to its tool's block output (Claude: `UserPromptSubmitHookSpecificOutput`, aliased as `ClaudeForwardDecision`). `evaluate(input)` receives the already-parsed, typed `TInput`; the dispatch convention below is how adapters implement it.

### 3.1 Two outcomes — forward or block

```ts
export type ForwardDecision<TBlockOutput = Record<string, unknown>> =
  | {
      decision: 'forward';
      payload: Record<string, unknown>[];
      retryOnce?: boolean;                        // resend once more if the first send failed
      finalize?: (accepted: boolean) => Promise<void>;  // commit-after-send; see below
    }
  | { decision: 'block'; reason: string; hookSpecificOutput: TBlockOutput };
```

`forward` carries the full list of records to push to the spool (the original parsed event, plus zero or more derived analytics events). `block` stops the hook and logs a reason; any extra fields on `block` (`claude-code-otlp` uses `hookSpecificOutput`, mirroring Claude Code's own hook-output JSON schema) are specific to that tool's blocking mechanism, not to this pattern — a different tool may have no `block` case at all, or a differently-shaped one.

`finalize` and `retryOnce` exist for a handler that owns a cursor into some external log (`claude-code-otlp`'s transcript offsets) and must not advance that cursor until the batch it derived from is actually durable. A handler with nothing to commit (the raw-passthrough fallthrough, a `block` decision) simply omits `finalize`. See §3.4 for the commit-after-send contract this enables.

### 3.2 One handler per event name — no `switch`, no shared merge step

```ts
protected async evaluate(parsed: TInput): Promise<ForwardDecision<TBlockOutput>> {
  // early-return / continuation-key checks here are tool-specific — only add
  // one if this tool's events need it (claude-code-otlp keys continuation on
  // its own 'session_id' field; a different tool may have no such field)

  const nativeEventName = readString(parsed, /* this tool's own event-name field */ 'event_name');
  if (nativeEventName === 'SomeEvent') {
    return await this.onSomeEvent(parsed);
  }
  // ...one `if` per handled event name...

  return { decision: 'forward', payload: [parsed] };
}
```

Each handler returns its own full `ForwardDecision`. The trailing fallthrough return is only for event names `evaluate()` doesn't branch on at all — it's not a sink that handled branches route through.

### 3.3 One parsed object, read directly — no typed projection

`parsed` is read directly by handlers (via small helpers like `readString`/`readOptionalString`) and forwarded as-is; there's no typed/camelCase projection layer, since for a handful of fields that adds a type to check against with no runtime-validation benefit.

### 3.4 One place writes to the spool, and a batch is all-or-nothing

The base class's `processOtlpEvent` is the only call site of `deps.forwardOtlpEventsToSpool`: after `evaluate()` resolves it computes the common (git, story, identity, project, version) and agent fields once (in parallel), builds the event for every `payload` record, then sends the whole invocation as **one batch** in **one request**. `forwardOtlpEventsToSpool` never throws, aborts after 3s, and returns a boolean (true only for a 2xx response); on `false` with `decision.retryOnce` set, the base class resends the same already-built events once more (same `event_id`s — never rebuilt) before giving up. The block path is unchanged: it prints the decision and returns before any enrichment. Handlers never forward anything themselves, so every event reaches the spool exactly once per attempt, in order, under the adapter's registered name.

**Commit-after-send.** A handler whose `ForwardDecision` carries a `finalize` is holding a resource (`claude-code-otlp`: the per-session parse-state lock, with its derived-but-not-yet-saved state) that must only be committed once the send is known to have landed. `processOtlpEvent` calls `finalize(accepted)` exactly once, in a `finally`, after the send attempt(s) — `accepted` is the boolean `forwardOtlpEventsToSpool` returned (after any retry). A handler's own `finalize` typically persists its state when `accepted` is true and always releases its lock, so a failed send leaves everything exactly as it was: the next hook re-derives and re-sends the same events from whatever log it reads (a transcript, for `claude-code-otlp`), with no separate retry queue needed. An empty `payload` skips straight to `finalize(true)` without resolving context or sending anything — there is nothing to lose, so no need to pay for git/identity/story resolution.

### 3.5 Proxy readiness is the adapter's own responsibility

The base flow calls `isTracked()` (abstract) before `deps.ensureOtlpProxy()`, so a subclass cannot skip the allowlist gate (the INVARIANT comment in the base flow). Past that, `ensureOtlpProxy()` runs for every event regardless of which handler runs (every `forward` decision needs the daemon up to reach the spool). Further gates (e.g. an auth check) remain the adapter's own decision. It additionally gates an SSO auth check inside `onUserPromptSubmit` only, because that's the one handler whose job is to enforce it. A different tool may not need a tracked-project concept at all, may not need proxy readiness for every event, or may need a different gate entirely — don't carry `claude-code-otlp`'s specific gating choices into a new adapter, just the principle that each adapter decides this for itself.

## 4. Adding a new event to an existing adapter

1. Write one handler method, `(input) => Promise<ForwardDecision<TBlockOutput>>`.
2. Add exactly one `if` branch in `evaluate()` dispatching to it. No `switch`, don't touch the trailing fallthrough.
3. Never forward from inside the handler — return the `ForwardDecision`; the base class's `processOtlpEvent()` sends it.
4. Add a test for the new branch, following the adapter's existing test structure.
5. Update that adapter's own event-surface table/notes (see §6 for the current example).

## 5. Adding a new `OtlpAgentAdapter` for a different tool

1. Create `src/agents/plugins/<new-adapter-name>/` with a class `extends OtlpAgentAdapter<TInput, TBlockOutput>` and implement `parseHookInput`, `extractHookContext`, `isTracked`, `evaluate` (following §3), `resolveAgentFields`, `resolveEventType` (the `type` for a native event without an explicit one) and `buildEventId` (the deterministic `<kind>:<session_id>:<discriminator>` — a natural key for events the adapter builds itself, a content hash for whatever is forwarded once per occurrence; see §6's `claude-code-otlp.event-id.ts` for the reference shape). Agent-owned common fields (platform, version, entrypoint, …) go in `resolveAgentFields()`, resolved **inside the adapter's own hook-time process**, not via a callback from the forwarder — the forwarder runs in the long-lived proxy daemon, a different process from the short-lived `codemie hook --agent <name>` CLI invocation, so resolving state there would reflect the daemon's environment. Git branch/remote, story, identity, project name and CLI version are already resolved by the base class. If resolving a field is expensive (subprocess spawn, network call), back it with a small file cache under `getCodemiePath()` — the hook-time process is fresh per event, so in-memory memoization buys nothing (see `client-version-cache.ts`).
2. Register it in `AgentRegistry` (`src/agents/registry.ts`) under its own `name` — same name the base class passes to `forwardOtlpEventsToSpool(events, name)` and matched by `AgentRegistry.getAnalyticsAgent(name)` in `hook.ts`.
3. Write a connector wiring the tool's native hooks/events to `codemie hook --agent <new-adapter-name>` (see `src/cli/commands/proxy/connectors/claude-code-otlp.ts` for the example — hook names, settings format, and env vars are tool-specific).
4. Everything from `forwardOtlpEventsToSpool` onward is already shared — no changes needed there as long as 1-3 hold. Only implement `finalize`/`retryOnce` on a handler's `ForwardDecision` if that handler owns a cursor into some external log that must not advance until its batch is durable (§3.4); a handler with nothing to commit omits both.

**`agent.git.snapshot` commit times.** Each `git_commits[].time` is normalized to an ISO-8601 UTC timestamp ending in `Z`; `git_commits[].files` is the number of changed files, not a list of paths.

**`PostCompact` / `agent.session.compact.done` (`openPostCompactPass`, `transcript/orchestrator.ts`).** `PostCompact` can fire before Claude Code has flushed the `compact_boundary` system line it reports on — observed lag ranges from under a second up to ~9s. Unlike every other pass in this module, `openPostCompactPass` does *not* hold the per-session lock for its whole duration:

1. A lock-free peek at the persisted `lastCompactionEnd` marker (`TranscriptParseState`), then a lock-free incremental scan every `COMPACTION_POLL_INTERVAL_MS` = 500ms: each tick reads only the bytes appended since the previous one (the shared `transcript-reader.ts` `readNewLines`, which cuts at the last newline so a partially flushed line is picked up by the next tick) and `JSON.parse`s only lines containing `compact_boundary`, so an idle poll over a multi-megabyte transcript costs one `stat`. A missing transcript ends the wait immediately instead of burning the budget. After finding new boundaries, polling continues until the set of newer boundaries has been unchanged for `COMPACTION_SETTLE_INTERVAL_MS` = 10s, or the total `POST_COMPACT_WAIT_BUDGET_MS` = 60s expires. In particular, when no marker is saved and the first boundary is already visible, it does not return immediately: it keeps polling so a later boundary can join the same batch. This quiet period accounts for delayed transcript flushes when the marker is empty or behind, reducing the chance that an older boundary is mistaken for the current compaction and allowing multiple newly visible boundaries to be collected together. No lock is held during the wait; holding it would stall sibling hooks for the same session.
2. After the quiet period or wait-budget expiry, the pass acquires the lock, reloads fresh state, runs the normal `deriveMainEvents` for `agent.usage.request`, and re-checks the accumulated scan — catching up on any bytes appended while the lock was being acquired — for every boundary newer than the fresh `state.lastCompactionEnd` (deliberately not scoped to `state.mainOffset`, which a sibling hook may have advanced). It appends one `agent.session.compact.done` record per boundary in transcript order and advances `lastCompactionEnd` to the last reported boundary, so a later pass does not re-emit them.

The `PostCompact` hook entry is also the one exception to every other event's synchronous, 30s-timeout entry: `connectors/claude-code-otlp.ts`'s `buildCodemieEntry()` gives it `async: true` plus `CODEMIE_POST_COMPACT_HOOK_TIMEOUT_SECONDS` (90s) instead of `CODEMIE_HOOK_TIMEOUT_SECONDS` (30s) — `async` keeps Claude Code, and the user's own turn, from ever waiting on this hook; the longer `timeout` is what keeps Claude Code from killing the subprocess before the wait above (plus the brief lock-held merge/send/commit after it) can finish. No other event can be `async`, because several of them depend on Claude Code waiting synchronously for a `ForwardDecision`-driven outcome (`UserPromptSubmit`'s SSO re-auth `block` decision being the clearest example).

See `docs/ARCHITECTURE-PROXY.md` for the proxy/daemon layer this hands off to, and `otlp-spool/` (`src/providers/plugins/sso/proxy/plugins/otlp-spool/`) for session completeness gating and draining — both already agent-agnostic and not something a new adapter needs to touch.

## 7. Evidence contract, classification and holds (EPMCDME-16440)

Applies to adapters that override `resolveEvidenceInputs()` (today only `claude-code-otlp`). Adapters that return `undefined` keep the legacy, unmarked path unchanged. The CLI only emits evidence; the backend decides destinations and access.

### 7.1 Hook-time evidence record

- **Location and key.** One JSON file per session in the `evidence/` directory under the CodeMie home (`evidenceDir()`, `record-store.ts`). The file name is `recordKey(apiIdentity, ownerHash, sessionId)`: a SHA-256 over length-prefixed parts, so no raw URL, e-mail or session id appears in file names.
- **Fields.** `session_id`, `launch_mode` (managed|native), `routed_via_codemie`, `routing_proof`, `organization`, `project`, `project_source` (linked_folder|profile|none), `repo_key`, `api_identity`, `owner_hash`, `profile`, plus `schema`, `created`, `last_used`.
- **Atomic publication.** Temp file, then `fs.link` to the final name; the loser of a race reads the winner back. Mode 0600.
- **Never repaired.** The first hook writes the record and it is then frozen. A mismatched key, other schema, corrupt file or oversized field yields `stamp_invalid`; the hook never rewrites it. Later hooks only read it and `touch` `last_used` at most once per day. A resumed session with a changed project, organization or routing still sends the original evidence.
- **Envelope marker.** Stamped hook lines carry `evidence_v: 1` on the spool line (`OtlpHookSpoolData`), never in event bodies. The marker is sticky once a pending line has it; a marked line without a valid record is `stamp_invalid` under every capability.
- **Source rules.** Organization comes from the key `oauthAccount.organizationName` in Claude's `.claude.json` (the value is never logged). Project is resolved once at stamping (env, pin, config) and frozen; an empty project sends no `X-CodeMie-Project` header. `repo_key` is the credential-free `host[:port]/path` form (`repoKeyFromRemote`), mirroring the backend normalization. Untracked projects stamp and spool nothing.

### 7.2 Routing proof and URL roles

Three URLs differ and must not be conflated: the **model upstream** (`CODEMIE_TARGET_API_URL`, preserved by `setupProxy`), the **local proxy** (loopback `CODEMIE_BASE_URL` the agent talks to) and the **analytics backend** (the daemon's `syncCodeMieUrl`, else `targetUrl`/`url`), resolved once per pass by `classification.resolveAnalyticsEndpoint`. Its canonical identity (scheme, host, port, base path) must equal the credentials' `api_identity` that keys the record, verdict and policy cache; a mismatch (stale daemon or credentials, another origin or deployment) sends and fetches nothing. The model upstream is never required to equal the analytics host; no hostname inference.

`routing_proof` is `proven` only when the proxy ran under the real provider/auth setup, the effective Anthropic endpoint (settings.json `env` over process env) is the proven local proxy, and the model target validates against the configured provider (managed), or the actual configured model route is derived (native). Positively direct routes are `proven` not routed: an empty `ANTHROPIC_BASE_URL` (the executor default), first-party Anthropic, and the Bedrock/Vertex flags (`CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`, true/1, without a custom provider base URL), read from process env and the user/project/local/managed settings layers. A native endpoint is routed only when it lies under the configured gateway at an origin plus path-segment boundary. A foreign override is `unproven`: the record classifies `unknown` (basis `routing_unproven`, local only, not in the sent enum), never `personal`.

### 7.3 Classify / decide seam

`classify(evidence, policy)` (`evidence/classify.ts`) returns a class and a sent basis (`routed`, `org_match`, `org_no_match`, `org_list_empty`, `no_org`, `policy_unavailable`). `decide()` maps it to `forward|suppress|withhold` through an optional consumer. `classification.ts` is the single decision site for the tick and the forwarder 409 path. `setClassificationConsumer(c)` is the plug-in point for opt-out (#711); the default forwards everything. `suppress` is a non-destructive no-op (nothing sent, no cursor, hold or loss change) and has no retention bound until #711 defines its terminal outcome. `withhold` becomes the hold `classification_unresolved`.

**Policy/capability cache** (`policy-cache.ts`, one `*.policy.json` per identity+profile namespace beside the records): a fetched policy is usable for 24 h; a failed refresh backs off 5 min; `legacy` capability is recorded only from an authenticated 404 and re-probed after 1 h; unknown capability is treated as possibly evidence-capable. **Sticky Personal (I5):** a first determinate `personal` verdict is stored (`verdict-store.ts`) and replaced only when class or policy version changes. Without a usable policy it is sent with full evidence or held `personal_not_forwardable`; evidence is never stripped.

### 7.4 Sending: structural proof and typed outcomes

Both the model proxy and the analytics sender use the typed `buildAttributionHeaders` contract owned by `header-injection.plugin.ts`. Its explicit `model` and `analytics` destinations construct separate header sets. The analytics caller supplies frozen evidence and an already validated classification; the builder performs no discovery, policy lookup or authentication changes. Security sign-off on the attribution contract and its derivation sources is still required before merge.

**Organization transport.** An organization the plain header cannot carry (not Latin-1 printable) is sent only as `X-CodeMie-Organization-Encoded: utf8-b64u.v1:<unpadded base64url of the original UTF-8>`, never in `X-CodeMie-Organization`, and only for routed=false sessions whose namespace (endpoint, owner, profile) has a usable policy listing `utf8-b64u.v1` in `organization_encodings`. Without that, the session is held `organization_encoding_unsupported` (evidence and bytes kept, policy re-read at most hourly, loss at the held-retention bound). A representable organization keeps the plain header unchanged, including on CodeMie-routed sends; an unrepresentable one is omitted when CodeMie-routed, and routing-unproven sends carry no organization at all. **Deployment gate:** the backend decoder must be released on EVERY serving instance before encoded CLI sends are activated (one instance advertising support does not prove the rest; an old backend ignores the extra header and cannot be made safe by client negotiation). Rolling back to an old backend while a CLI has the capability cached is unsafe until encoded sends are stopped or the cache is cleared. Evidence sends add `X-CodeMie-Session-Id`, `-Routed-Via-CodeMie`, `-Organization`, `-Project-Source`, `-Subscription-Type`, `-Policy-Version`, `-Repo-Remote` and `X-CodeMie-Project`, all from the frozen record. Payload bytes are never rewritten. Before sending, OTLP bodies pass a structural proof (`proveRange`: session, project, signal) and hook lines `proveHookLines`; only the **verified prefix** is sent, byte-identical, and the cursor advances by that length. An unverified remainder holds (`otlp_unparseable`, or a specific reason via `noteStreamHold`). Evidence reads are bounded windows (at most 5 MiB) cut at resource-entry boundaries: an entry running past the window waits for the next window (never cut), so a larger backlog drains window by window with exact cursors; one entry over the cap holds `otlp_entry_too_large`. When the unproven route carries a known organization the `X-CodeMie-Organization` header is omitted, because the backend derives Personal from routed=false plus a non-matching organization and would contradict the client's `unknown`.

`response.ts` is the single response consumer; `decodeResponse` yields a `SendOutcome.kind`: `ok`, `discarded` (hooks `accepted:0` with a reason, or OTLP `rejected>0`), `stale` (409 `stale_policy`), `retry` (5xx, network), `failed`, `auth-expired`. A 2xx whose body cannot be verified is never an acknowledgement: a failed or timed-out body read is `retry` (`response_read_failed`), an oversize body `failed` (`response_too_large`), malformed JSON/protobuf or wrong field types `failed` (`response_malformed`); only a valid hooks object or a valid (or genuinely empty) OTLP response is `ok`/`discarded`. The policy probe uses the same bounded read. `ok` and `discarded` advance exactly the request range; the others retain. A `stale` outcome forces a policy refresh and resends once only if the version changed. The latest acknowledged discard reason is persisted as `lastDiscard` in session status.

### 7.5 Hold and loss reasons

Every holding path has a named reason. Holds live in session status (`holds.session` or per stream); the first-hold time survives restarts and reason changes. Past `heldRetentionMs()` (`OTLP_HELD_RETENTION_MINUTES`, default 1440) the pending bytes are discarded and recorded as `lastLoss` (persisted) plus a `logger.warn`.

| Reason | Meaning | Recorded |
|---|---|---|
| `stamp_pending` | marked/new OTLP-only session, record not yet visible | hold; on expiry loss `no_evidence_timeout` |
| `stamp_invalid` | record corrupt, mismatched key or unreadable; marked line without a valid record | hold; loss with same reason |
| `evidence_capacity` | record store at cap with every record pinned (the hook first evicts idle records with no pending spool) | nothing enqueued; the hook reports the dropped events and the daemon records `lastLoss` (events kept by a cursor are retried instead) |
| `verdict_unavailable` | the sticky verdict cannot be read or persisted (durable privacy state) | hold; loss; never a legacy or evidence-free send |
| `otlp_entry_too_large` | one OTLP resource entry exceeds the 5 MiB window | stream hold; loss |
| `personal_not_forwardable` | sticky Personal, no usable policy, not full-evidence capable | hold; loss |
| `classification_unresolved` | consumer `withhold` or classification not determinable | hold; loss |
| `session_mismatch`, `session_id_absent` | session id missing or differing from the record | hold; loss |
| `project_conflict` | hook project differs from the bound/record project | hold; loss |
| `analytics_endpoint_mismatch` | the daemon's analytics URL does not canonicalize to the credentials' `api_identity`; nothing is sent or fetched | session hold; loss |
| `organization_encoding_unsupported` | routed=false, known organization the plain header cannot carry (non-Latin-1), and the namespace's usable policy does not advertise `organization_encodings: ["utf8-b64u.v1"]` (also under sticky Personal/policy loss) | session hold, bytes and evidence kept; re-read hourly; loss at the held-retention bound (default 24 h) |
| `otlp_unparseable` | OTLP range not provable and no more specific reason | stream hold; loss |
| `no_evidence_timeout` | loss only: an expired `stamp_pending` | `lastLoss` |
| `unstamped_legacy` | not a hold: a pre-epoch or legacy-capability unmarked session sent on the legacy path | decision basis |

Backend refusals (for example `session_project_conflict`) are acknowledged discards stored as `lastDiscard`, not holds.

### 7.6 Lifetime and retention

- **Records are not spool state.** The spool sweep drains and removes spool data but keeps records. `sweepSpool` also runs record retention: idle records (default 90 days, `CODEMIE_EVIDENCE_RECORD_IDLE_DAYS`) and, oldest-first, records over the file cap (default 20,000, `CODEMIE_EVIDENCE_RECORD_MAX_FILES`) are evicted, except records of sessions with pending spool bytes. If pending sessions block the cap, new stamps fail with `evidence_capacity` until they drain.
- **Client policy only.** Local eviction is a client decision. The backend keeps raw analytics for 90 days but keeps the session-to-project binding indefinitely by default, so a session re-stamped after local eviction is not proof of a fresh server session and may legitimately be answered `session_project_conflict`.
- `epoch.json` in the spool root separates pre-existing (legacy, unmarked) sessions from new ones.
